POWERFORGE — PHASE 3 IMPLEMENTATION
DOCUMENT PROCESSING AND STABLE PAGE REPRESENTATION

You are implementing Phase 3 of PowerForge.

Phase 0 established the repository and application architecture.
Phase 1 implemented project and revision management.
Phase 2 implemented immutable document storage, RevisionDocument associations,
revision inheritance, MinIO/S3-compatible storage, document metadata, and the
revision document UI.

Phase 3 must build the processing layer that converts immutable uploaded
documents into stable logical pages and reusable derived artifacts.

DO NOT implement OCR, AI, document classification, equipment extraction,
topology, or the engineering model in this phase.

2. PHASE 3 GOAL
======================================================================

Phase 3 turns each immutable Document into a stable, machine-consumable page
representation.

Conceptually:

    RevisionDocument
          │
          ▼
       Document                  immutable original
          │
          ▼
     DocumentPage                stable logical page identity
          │
          ▼
     PageArtifact                derived processing output

Processing metadata is tracked separately:

       Document
          │
          └── DocumentProcessingRun

At the end of Phase 3, PowerForge must be able to process:

    PDF
    PNG
    JPEG / JPG
    TIFF / TIF

and expose:

    - logical pages
    - page dimensions/orientation
    - analysis-quality page render
    - thumbnail
    - native PDF text where available
    - processing state/progress
    - retry behavior
    - signed access to derived artifacts

No semantic interpretation is performed yet.

======================================================================
3. CRITICAL ARCHITECTURAL RULE
======================================================================

PROCESSING BELONGS TO Document, NOT RevisionDocument.

A Document represents immutable bytes.

If the same Document is referenced by:

    Revision 0
    Revision 1
    Revision 2

through three RevisionDocument rows, the original bytes must normally be
processed only once.

Correct:

    RevisionDocument ─┐
    RevisionDocument ─┼──► Document
    RevisionDocument ─┘        │
                               ▼
                         DocumentPages
                               │
                               ▼
                         PageArtifacts

Incorrect:

    Revision 0 → independent pages
    Revision 1 → duplicate pages
    Revision 2 → duplicate pages

Revision inheritance must reuse existing processing automatically.

======================================================================
4. DOCUMENTPAGE — STABLE PAGE IDENTITY
======================================================================

Create a DocumentPage entity representing a logical page/frame in the immutable
source Document.

DocumentPage must belong directly to Document.

Suggested fields:

    id
        UUID primary key

    document_id
        UUID FK → documents.id
        NOT NULL

    page_number
        positive integer
        1-based

    source_width
        numeric / float
        NOT NULL

    source_height
        numeric / float
        NOT NULL

    source_unit
        enum or constrained value:
            POINTS
            PIXELS

    rotation_degrees
        integer
        one of 0, 90, 180, 270

    native_text_char_count
        integer
        default 0

    created_at
        timestamp

Constraint:

    UNIQUE(document_id, page_number)

DocumentPage identity MUST NOT depend on:

    processing run
    render DPI
    image dimensions
    AI provider
    revision

Reason:

Future evidence will reference stable source locations such as:

    Document
        ↓
    DocumentPage 17
        ↓
    normalized bounding box

Re-rendering a page later must not change its logical identity.

source_width and source_height are the upright logical page after rotation
normalization: the page as displayed. They are not the unrotated PDF media box
when the source rotation is 90 or 270. A 90 or 270 degree rotation swaps the
stored width and height relative to that unrotated source.

rotation_degrees is the source rotation that was applied to produce the
upright page. PDF pages use POINTS. PNG, JPEG, and TIFF frames use PIXELS.

The analysis image is this same upright page. Later normalized coordinates
(section 10) refer to it, not to rendered pixels and not to the unrotated
media box.

5. SOURCE PAGE SEMANTICS
======================================================================

PDF:

    one PDF page = one DocumentPage

PNG / JPEG:

    entire image = DocumentPage 1

TIFF:

    each TIFF frame = one DocumentPage

Example:

    multipage.tiff
        frame 1 → page 1
        frame 2 → page 2
        frame 3 → page 3

Page numbering is always 1-based in the PowerForge domain/API.

6. DOCUMENTPROCESSINGRUN
======================================================================

Create DocumentProcessingRun to track processing of a Document under a specific
processing pipeline/profile.

Suggested fields:

    id
        UUID

    document_id
        UUID FK → documents.id

    processor_version
        string

    profile_version
        string

    profile_hash
        string

    status
        enum:
            PENDING
            RUNNING
            COMPLETED
            FAILED

    pages_total
        nullable integer

    pages_processed
        integer default 0

    attempt_count
        integer
        set once when the run is inserted
        1 for the first attempt, then 2, 3, ...
        never incremented later, including when the worker claims the run

    created_at
    started_at
    completed_at
    failed_at

    error_code
        nullable string / enum

    error_message
        nullable text

A processing target is:

    document_id
    + processor_version
    + profile_hash

A DocumentProcessingRun is one attempt at that target, not a row that is
reset and reused. Retry inserts a new run. Previous attempts stay as they
finished.

    Document + profile
        ├── Run 1  FAILED
        ├── Run 2  FAILED
        └── Run 3  COMPLETED

Each run has its own id, so its artifacts live under a different storage
prefix. put() never has to overwrite a key from an earlier attempt.

For one processing target there is at most one run whose status is PENDING,
RUNNING, or COMPLETED. Many FAILED runs are allowed. Enforce that with a
partial unique index on (document_id, processor_version, profile_hash)
WHERE status IN ('PENDING', 'RUNNING', 'COMPLETED'), plus a transactional
insert. Two concurrent retries must not create two active runs.

The current run for a target is that single non-failed run when one exists.
When every attempt failed, the current run is the latest FAILED run. APIs
and the document list report the current run only. Phase 3 does not offer a
view of older attempts.

        normalized relative to the logical page

        x      0.0 → 1.0

11. ANALYSIS IMAGE
======================================================================

Use a lossless format appropriate for drawings, preferably PNG unless existing

For PDFs:

    render the complete page.

For input images:

    normalize orientation/color representation and produce the canonical

Do NOT alter engineering information through aggressive enhancement.

Allowed normalization includes:

    EXIF orientation handling
    page rotation normalization
    predictable color mode
    alpha handling
    safe format conversion
    bounded resolution

Do NOT automatically apply:

    OCR thresholding
    sharpening
    deskew
    denoising
    contrast enhancement
    cropping
    line removal
    background removal

======================================================================
12. LARGE DRAWING RESOURCE LIMITS
======================================================================

Engineering drawings may be extremely large.

Do NOT blindly render every PDF page at a fixed high DPI.

Define a configurable processing profile with sensible defaults.

Suggested initial profile:

    target_dpi:
        200

    max_long_edge_px:
        8000

    max_total_pixels:
        50_000_000

    thumbnail_long_edge_px:
        800

A PDF page or a decodable image whose analysis image would exceed
max_long_edge_px or max_total_pixels is scaled down proportionally. Do not
fail a run merely because the full-resolution render would be large.

Record:

    actual output width and height
    effective DPI for a PDF page after that scale-down

For an image, effective_dpi is the source DPI multiplied by the scale factor
when the source DPI is known, and null otherwise. Output pixel dimensions are
always stored.

Input that cannot be decoded fails the run. That includes a corrupt file and
a decompression bomb. Pillow's decompression-bomb ceiling for this phase is
the configured input ceiling (MAX_IMAGE_PIXELS, the Phase 2 upload cap), not
Pillow's library default. A file Phase 2 accepted must still open. A file
beyond that ceiling, or one whose decoded size exceeds the ceiling, fails
with RESOURCE_LIMIT_EXCEEDED.

Processing must never create an unbounded image.

Later phases may perform targeted high-resolution region rendering from the
original PDF. Do NOT implement region rendering now.

16. ASYNCHRONOUS PROCESSING
======================================================================

Document processing must run in the existing document worker / Celery
infrastructure.

Do NOT process PDF pages inside the upload HTTP request.

Publish document-processing tasks to a dedicated Celery queue that only
document-worker consumes. The extraction and validation workers share the
default queue today and will take a task they do not implement. A stolen
task leaves the run PENDING and unclaimed.

After successful Phase 2 document creation:

    Document committed
        ↓
    ensure processing run exists
        ↓
    queue document-processing task on the dedicated queue
        ↓
    HTTP request finishes independently
        ↓
    document-worker performs processing

If task enqueue fails:

    keep the PENDING run
    the Document remains valid
    log the queue failure

Do not invalidate the original upload. Do not mark the run FAILED solely
because the broker rejected the message. A later ensure or the backfill
command enqueues an unclaimed PENDING run again. The explicit retry route
is only for FAILED.

======================================================================
17. ENSURE-PROCESSING SERVICE
======================================================================

Implement a clear service operation equivalent to:

    ensure_document_processing(document_id)

Behavior:

Evaluate the current run for the processing target in this order:

If the current run is COMPLETED:

    return it
    do not reprocess
    do not enqueue

If the current run is RUNNING:

    return it
    do not enqueue

If the current run is PENDING and no worker has claimed it:

    return it
    enqueue the processing task again
    do not create a second run

If the current run is FAILED:

    return that latest failed run
    do not enqueue
    do not create a second run
    explicit retry is the only way to start another attempt

If no run exists:

    create one PENDING run with attempt_count = 1
    enqueue it
    return it

Read endpoints must not call ensure. Polling status must not publish tasks.

Repeated ensures while a run is still PENDING may publish more than one
task. That is safe: the claim in section 19 succeeds for only one worker.
The extra deliveries must not write pages or artifacts.

This operation must be concurrency-safe. Two simultaneous ensures for the
same target must not create two runs.

======================================================================
18. RETRY SEMANTICS
======================================================================

Retry applies only when the current run for the target is FAILED. It does
not reuse that run and it does not delete that run's rows or objects.

Insert a new PENDING run for the same processing target:

    attempt_count = (number of existing runs for the target) + 1
    pages_processed = 0
    enqueue the new run on the dedicated queue
    leave every previous FAILED run unchanged, including its error fields,
    progress counters, page_artifacts rows, and stored objects

The new run gets a new id and therefore a new artifact prefix. put() writes
only those new keys. It does not overwrite the failed attempt.

Do not delete DocumentPage rows. The new attempt reconciles the same logical
pages and attaches new PageArtifact rows to them. Page identity survives
retry.

Do not retry when the current run is PENDING, RUNNING, or COMPLETED, and do
not retry when no run exists. A second concurrent retry loses the partial
unique index in section 6; return the PENDING run that won, and do not
insert another.

A materially different processing configuration is a new processing target,
not a retry of the old one.

Phase 3 does not garbage-collect derived objects left by failed attempts.
That is the same class of debt as orphaned originals from Phase 2. Do not
build a screen for browsing those old attempts.

======================================================================
19. WORKER PROCESSING FLOW
======================================================================

The worker should perform approximately:

    Load processing run
        ↓
    atomically claim it
        ↓
    status = RUNNING
    attempt_count stays at the value set when the run was inserted
        ↓
    fetch immutable Document from object storage
        ↓
    fully decode/open source
        ↓
    discover logical pages
        ↓
    create/reconcile DocumentPage rows
        ↓
    for each page:
        render/normalize analysis image
        generate thumbnail
        extract native PDF text where applicable
        write artifacts to object storage
        persist artifact metadata
        increment pages_processed
        ↓
    validate full page set
        ↓
    status = COMPLETED

Only one worker may successfully claim the same processing run at a time.
Claim is an atomic transition from PENDING to RUNNING. A duplicate delivery
that finds the run already RUNNING or beyond must return without writing and
without changing attempt_count.

A new attempt reconciles existing DocumentPage rows and writes artifacts
only under its own run id. It does not modify the previous attempt's
artifacts and it does not delete the original Document.

======================================================================
20. COMPLETION GUARANTEE
======================================================================

A processing run may be marked COMPLETED only when the full expected page set
and all required artifacts were produced successfully.

If a 100-page document fails on page 72:

    run status = FAILED

Do NOT expose the partial result as successfully processed.

The pages API and artifact URL API return a result only when the compatible
run is COMPLETED. While a run is PENDING, RUNNING, or FAILED, those routes
do not return page metadata or artifact URLs. Progress for a RUNNING run
comes from the processing-status payload (pages_processed and pages_total),
not from the pages list.

Downstream phases must be able to assume:

    COMPLETED = complete internally consistent processing result

A failed attempt keeps its derived objects and page_artifacts rows. They are
not a successful result: the pages and artifact URL routes look only at the
COMPLETED run. Retry does not remove them (section 18). Do not delete the
original Document, and do not mark a partial run COMPLETED in order to hide
it.

Do not damage or delete the original Document.

23. STORAGE ABSTRACTION
======================================================================

Do not bypass the Phase 2 ObjectStorage abstraction from processing code.

The worker must not import the FastAPI application to reach that abstraction.
ObjectStorage, its in-memory and S3 implementations, and the processing
service live in a library that both services/api and services/document-worker
depend on. That library also owns the SQLAlchemy mappings the worker loads,
including Document, so there is one mapping of the documents table. Do not
add a second Document class in the worker.

packages/document-model keeps the pure vocabulary: processing and artifact
enums, failure codes, the processing profile, its hash, and artifact key
construction. It must not depend on SQLAlchemy, Celery, FastAPI, boto3,
Pillow, or PyMuPDF.

PyMuPDF and Pillow belong to the processing implementation the worker runs.
The Celery task lives in document-worker and calls the processing service.
It does not contain the processing implementation inline.

The document-worker image installs that shared library, document-model,
PyMuPDF, Pillow, the database driver, and boto3. Its Compose environment
gets DATABASE_URL and the same S3_* settings as the API, with
S3_ENDPOINT_URL aimed at MinIO on the Compose network and
S3_PUBLIC_ENDPOINT_URL aimed at the browser-reachable endpoint used for
signed URLs.

API, worker, and domain code must not become tightly coupled to MinIO.

Signed URLs for derived artifacts should use the same security pattern as
Phase 2 originals.

25. API
======================================================================

Keep APIs revision-scoped where this is useful for access-control validation,
even though processing belongs to Document.

An association is enough. INCLUDED and REMOVED both may read processing
status, pages, and artifact URLs, including when the revision is SUPERSEDED
or the project is ARCHIVED or CANCELLED. That matches Phase 2 download.
Retry is allowed through any of those associations. Processing is not a
revision mutation, so revision read-only rules do not block it.

The existing revision-document list and detail responses include a processing
summary for the current run of each row: status, attempt_count,
pages_processed, pages_total, error_code, and a concise error_message. The
current run is defined in section 6. A document with no run yet reports that
absence. Do not include older failed attempts in this summary.
The documents table must be able to render its processing column from this
list. Do not require one status request per row.

Add routes equivalent to:

PROCESSING STATUS

    GET
    /api/projects/{project_id}/revisions/{revision_id}/documents/
        {revision_document_id}/processing

Return at minimum:

    processing status
    progress
    page count when known
    attempt count
    failure information when failed
    processor/profile information where useful

RETRY

    POST
    /api/projects/{project_id}/revisions/{revision_id}/documents/
        {revision_document_id}/processing/retry

This route creates a new PENDING run only when the current run is FAILED
(section 18). PENDING is re-queued by ensure and by backfill, not by this
route. COMPLETED and RUNNING are rejected. The response is the new run.

PAGES

    GET
    /api/projects/{project_id}/revisions/{revision_id}/documents/
        {revision_document_id}/pages

Return stable DocumentPage metadata and artifact information only when the
compatible run is COMPLETED. Otherwise do not return pages or artifact URLs.
The client uses the processing-status payload for progress.

PAGE DETAIL

    GET
    .../pages/{page_id}

ARTIFACT URL

    GET
    .../pages/{page_id}/artifacts/{artifact_type}/url

Return a short-lived signed URL. This route also succeeds only when the
compatible run is COMPLETED.

Exact route organization may follow established repository conventions.

All routes must verify:

    project
    revision
    RevisionDocument
    DocumentPage

belong to the expected chain.

Cross-project access must be rejected.

27. PROCESSING AND REVISION MUTABILITY
======================================================================

Document processing is a property of immutable Document bytes.

Therefore processing may continue, be retried, or be viewed even if a
revision becomes SUPERSEDED, and even if the RevisionDocument in that
revision is REMOVED. The Document may also belong to other revisions.

Do not treat processing or retry as a revision mutation. Revision read-only
rules do not apply to them.

Access through a revision-scoped API must still validate that a
RevisionDocument associates that Document with that revision. INCLUDED and
REMOVED both qualify. A page must belong to that Document.

pure domain package:

    FastAPI
    SQLAlchemy
    Celery
    MinIO/S3 SDK calls
    Pillow
    PyMuPDF

The processing service, ObjectStorage and its implementations, and the
SQLAlchemy models the worker must load live in a shared library imported by
both services/api and services/document-worker. The worker must not import
the FastAPI application. Details are in section 23.

The Celery task lives in the worker and calls that service. It must not
contain the processing implementation inline.

31. TESTING — REQUIRED
======================================================================

Phase 3 is not complete without automated tests.

At minimum cover:

PDF

- single-page PDF
- multipage PDF
- correct page count
- page ordering
- native PDF text extraction
- scanned/image-only PDF succeeds with zero native text and no NATIVE_TEXT
  artifact
- rotated page stores the upright displayed width and height, and records
  rotation_degrees as the source rotation that was applied
- corrupt PDF fails cleanly
- password-protected PDF fails cleanly

IMAGES

- PNG produces one DocumentPage
- JPEG produces one DocumentPage
- EXIF orientation handled correctly
- single-page TIFF
- multipage TIFF creates multiple pages
- malformed image fails cleanly

ARTIFACTS

- analysis image created
- thumbnail created
- native-text artifact created only when extracted text is non-empty
- whitespace-only PDF text does not create a NATIVE_TEXT artifact
- artifact metadata/hashes persisted
- artifacts private
- signed URL access works

RESOURCE CONTROL

- a decodable page larger than the profile cap is scaled down and records
  effective DPI (PDF) or output dimensions (image)
- decompression-bomb style input, and input that cannot be decoded, fails
  the run
- large PDF rendering is bounded by profile limits
- a file within the Phase 2 upload ceiling still opens under Pillow's bomb
  guard

PROCESSING STATE

- PENDING → RUNNING → COMPLETED
- failure results in FAILED
- partial processing never becomes COMPLETED
- pages and artifact URLs are withheld until COMPLETED
- progress is visible from the processing-status payload while RUNNING
- retry of a FAILED current run inserts a new PENDING run and leaves the
  failed run, its counters, and its artifacts unchanged
- the new run has its own storage prefix and attempt_count one higher than
  the previous attempt
- attempt_count is set at insert and does not change when the worker claims
- a second claim of the same run does not write artifacts
- two simultaneous retries leave only one new PENDING run
- the new run starts at pages_processed 0
- an unclaimed PENDING run is enqueued again by ensure
- a lost enqueue leaves the Document valid and the run PENDING
- backfill re-enqueues an unclaimed PENDING run and does not retry FAILED
- the document list and detail payloads include the processing summary

IDEMPOTENCY / CONCURRENCY

- repeated ensure-processing returns the same compatible run
- ensure of a RUNNING or COMPLETED run does not enqueue
- two simultaneous ensure requests do not create duplicate logical runs
- duplicate Celery delivery does not duplicate pages/artifacts
- document-processing tasks are published to the queue only document-worker
  consumes

REVISION REUSE

Given:

    Revision 0 → Document A
    Revision 1 → inherited Document A
    Revision 2 → inherited Document A

verify there is:

    one Document
    multiple RevisionDocuments
    one stable DocumentPage set
    one compatible completed processing result

ACCESS CONTROL BOUNDARIES

- cross-project page access rejected
- page must belong to expected Document
- RevisionDocument association required for revision-scoped access
- REMOVED associations, and associations on a SUPERSEDED revision, can read
  processing status and, once COMPLETED, pages and artifact URLs
- those same associations can retry a FAILED run

FAILURE SAFETY

- storage read failure fails processing cleanly
- artifact storage failure does not damage original
- original Phase 2 object remains unchanged after any processing failure

REGRESSION

- Phase 1 and Phase 2 tests continue to pass

The ADR should record:

1. Processing belongs to Document, not RevisionDocument.
2. DocumentPage is stable and independent of processing resolution/version.
3. Page numbers are 1-based.
4. PDF pages / image files / TIFF frames map to logical pages as specified.
5. Original Documents remain primary evidence.
6. PageArtifacts are derived data.
7. Processing is asynchronous.
8. Processing is version/profile aware.
9. Compatible processing is idempotent and reused across revisions.
10. Native PDF text extraction is Phase 3; OCR is deferred.
11. Normalized top-left coordinates on the upright logical page are the
    future provenance convention.
12. A decodable page that would exceed the profile pixel cap is scaled down.
    Input that cannot be decoded, including a decompression bomb, fails.
13. source_width and source_height are the upright displayed page.
    rotation_degrees is the source rotation that was applied.
14. A DocumentProcessingRun is one attempt. Retry inserts a new run under
    the same processing target and keeps the failed attempt's rows and
    objects. attempt_count is set at insert and is not changed on claim.
    At most one PENDING, RUNNING, or COMPLETED run exists per target.
15. ensure and backfill re-enqueue an unclaimed PENDING run. They do not
    create a run when the current run is FAILED. Retry is only for FAILED.
16. Pages and artifact URLs are exposed only for a COMPLETED run.
17. The revision-document list carries processing status.
18. REMOVED and superseded associations may read and retry processing.
19. The API and document-worker share the ObjectStorage port and the
    processing service. The worker does not import the FastAPI application.
    Processing tasks use a dedicated queue.
20. A page with no native text stores native_text_char_count = 0 and no
    NATIVE_TEXT artifact.
