============================================================
1. PHASE OBJECTIVE
============================================================

Implement the foundational Project Management domain.

The goal is to allow an engineer to:

1. Create a project.
2. View a list of projects.
3. Open a project.
4. Edit project information.
5. Pause, resume, cancel, archive, and unarchive a project.
6. Create project revisions.
7. View revision history.
8. Select a revision as the active/current revision.
9. View basic project/revision status.

This phase establishes the organizational structure that all future modules will use.

The application should conceptually support:

Project
    ├── Revision 1  → (future) documents, extraction, engineering model
    ├── Revision 2  → (future) documents, extraction, engineering model
    └── Revision 3  → (future) documents, extraction, engineering model

There is one revision entity: ProjectRevision. Documents, extraction jobs, and the
engineering model attach to that entity in later phases. There is no separate
"model revision" table.

============================================================
3. PROJECT DOMAIN
============================================================

Create a Project domain entity.

A project should contain, at minimum:

- id
- project_number
- project_name
- project_address
- project_scope
- engineer_names
- client_name
- description
- status
- created_at
- updated_at
- archived_at
- created_by

`project_address` is the project location. Do not add a separate `location` field.

`engineer_names` is a list of free-text names (PostgreSQL text array or JSONB list).
There is no users table in Phase 1. Do not create one. A users table arrives with
authentication; engineer names can be migrated to user references later.

`created_by` is a nullable UUID with no foreign key. It becomes a non-null FK to
users when authentication is implemented.

Project status:

ACTIVE
PAUSED
CANCELLED
ARCHIVED

New projects start as ACTIVE. `archived_at` is null until the project is archived
and is cleared when the project is unarchived. `status_before_archive` records the
status at archive time and is cleared on unarchive.

Use a PostgreSQL enum (or equivalent constrained type), not unconstrained strings.

Project numbers are unique and immutable after create.

Project IDs are UUIDs generated with `gen_random_uuid()` (pgcrypto, enabled in
Phase 0 migration `0001_enable_extensions`).

============================================================
4. PROJECT REVISION DOMAIN
============================================================

Create a ProjectRevision entity.

A revision belongs to exactly one project.

This is the single revision documents and the engineering model will attach to.
"Model revisions" in ENGINEERING_MODEL.md means the model snapshot stored on a
ProjectRevision in a later phase, not a second revision table.

At minimum, support:

- id                 (UUID primary key)
- project_id
- identifier         (human-readable revision code; not the UUID)
- description
- status
- created_at
- updated_at
- created_by         (nullable UUID, no FK, same rule as Project)

Do not name the human-readable code `revision_id`. That name is reserved for
UUID foreign keys (for example future `equipment.revision_id` → `project_revisions.id`).

Revision status:

DRAFT
ACTIVE
SUPERSEDED

New revisions are always persisted as DRAFT.

Activate is the only way a revision becomes ACTIVE. `create_revision` must not
write ACTIVE itself. If the user chooses to activate at create time, the service
persists DRAFT and then calls `activate_revision` in the same transaction.

Only one revision may be ACTIVE for a project at any time. Enforce this with a
partial unique index, for example:

    UNIQUE (project_id) WHERE status = 'ACTIVE'

Activating a revision must atomically:

- set the previous ACTIVE revision (if any) to SUPERSEDED
- set the selected revision to ACTIVE

Do not delete old revisions. Historical revisions remain accessible.

A project may have zero revisions. A project may have only DRAFT revisions and
no ACTIVE revision.

============================================================
5. REVISION IDENTIFIERS
============================================================

Allow human-readable identifiers such as:

- 0
- 1
- 2
- A
- B
- C
- ABC-IFC
- IFC-REV-1
- ABC-IFC-REV-2

Do not assume revisions are numeric.

Store `identifier` separately from the internal UUID `id`.

`identifier` is unique per project: UNIQUE (project_id, identifier).

API paths use the UUID (`{revision_id}` means `project_revisions.id`), not the
human-readable identifier. The UI displays the identifier.

6. DATABASE
============================================================

Create the necessary PostgreSQL tables and Alembic migrations.

At minimum:

projects
project_revisions

Do not create a users table in this phase.

Create appropriate:

- primary keys (UUID, `gen_random_uuid()`)
- foreign keys (`project_revisions.project_id` → `projects.id`)
- indexes
- unique constraints (`projects.project_number`; `(project_id, identifier)`;

The project revision relationship must enforce referential integrity.

Do not ON DELETE CASCADE project revisions when a project row is removed.
Normal UI workflow never physically deletes a project.

7. API
============================================================

Implement REST APIs following the conventions established in Phase 0.
`{project_id}` and `{revision_id}` are UUIDs.

Project endpoints:

POST   /api/projects
GET    /api/projects
GET    /api/projects/{project_id}
PATCH  /api/projects/{project_id}
POST   /api/projects/{project_id}/pause
POST   /api/projects/{project_id}/resume
POST   /api/projects/{project_id}/cancel
POST   /api/projects/{project_id}/archive
POST   /api/projects/{project_id}/unarchive

Revision endpoints:

POST   /api/projects/{project_id}/revisions
GET    /api/projects/{project_id}/revisions
GET    /api/projects/{project_id}/revisions/{revision_id}
PATCH  /api/projects/{project_id}/revisions/{revision_id}
POST   /api/projects/{project_id}/revisions/{revision_id}/activate

GET /api/projects supports:

- search on project_number and project_name only
- filter by status

PATCH /api/projects/{project_id} accepts metadata only:

- project_name
- project_address
- client_name
- project_scope
- engineer_names
- description

PATCH must reject `status` and `project_number`. Status changes use the action
endpoints above.

PATCH /api/projects/{project_id}/revisions/{revision_id} accepts:

- description
- identifier

PATCH revision must reject `status`. Activation uses POST .../activate.

POST /api/projects does not create a revision. The first revision is a separate
explicit create. The create-project UI may offer an optional "also create first
revision" step that calls the revision API; it must not be implicit in
create_project().

Do not expose ORM/database models directly through the API.

Use Pydantic request/response schemas.

Validate all incoming data.

Return appropriate HTTP status codes and meaningful error responses.

============================================================
11. REVISION MANAGEMENT UI
============================================================

Allow the engineer to:

- Create a revision (identifier + optional description; optional activate)
- View revision history
- Open a revision
- Activate a revision

Opening a revision in Phase 1 shows a placeholder page stating that revision
workspace content (documents, model, extraction) is not implemented yet. Do not
fake those features.

When activating a revision:

Current ACTIVE revision:
    becomes SUPERSEDED

Selected revision:
    becomes ACTIVE

This operation must be atomic.

Do not allow a project to end up with two active revisions because of
concurrent requests.

Activating a revision that is already ACTIVE may be idempotent.

SUPERSEDED revisions cannot be activated.

Only a revision created after the current ACTIVE revision may be activated
(compared by created_at). Older DRAFT revisions remain DRAFT and cannot jump
ahead of the current active line. If the project has no ACTIVE revision, any
DRAFT may be activated.

============================================================
12. PROJECT LIFECYCLE
============================================================

Projects are never physically deleted in the normal UI workflow.

Status transitions:

    ACTIVE   ↔  PAUSED
    ACTIVE   →  CANCELLED
    PAUSED   →  CANCELLED
    ACTIVE | PAUSED | CANCELLED | ARCHIVED  →  ARCHIVED
    ARCHIVED →  status_before_archive (ACTIVE, PAUSED, or CANCELLED)

There is no direct CANCELLED → ACTIVE or CANCELLED → PAUSED.
Archive is a filing action. Unarchive restores the pre-archive status; it does
not uncancel. Existing archived rows with no recorded history restore to ACTIVE.

Action endpoints:

- POST .../pause      ACTIVE → PAUSED
- POST .../resume     PAUSED → ACTIVE
- POST .../cancel     ACTIVE or PAUSED → CANCELLED
- POST .../archive    any non-archived → ARCHIVED; set archived_at and
                      status_before_archive
- POST .../unarchive  ARCHIVED → status_before_archive or ACTIVE if null;
                      clear archived_at and status_before_archive

Reject other transitions with a clear error.

When a project is ARCHIVED:

- status is ARCHIVED and archived_at is set
- PATCH project is rejected
- creating revisions is rejected
- activating a revision is rejected
- PATCH revision is rejected
- pause / resume / cancel are rejected
- unarchive is allowed
- historical rows remain intact
- the UI clearly indicates archived status

Unarchive restores `status_before_archive`. If that value is missing (legacy
archived rows), restore ACTIVE.

PAUSED and CANCELLED projects:

- PAUSED projects may still be edited and may still receive revisions.
- CANCELLED projects are read-only (same write restrictions as ARCHIVED):
  PATCH, new revisions, activate, and pause/resume/cancel are rejected.
  Archive is still allowed (CANCELLED → ARCHIVED).

============================================================
16. ERROR HANDLING
============================================================

Handle cases such as:

- Duplicate project number
- Project not found
- Revision not found
- Revision belongs to another project
- Attempt to PATCH an archived project
- Attempt to create or activate a revision on an archived project
- Invalid revision identifier (empty, or duplicate within the project)
- Attempt to activate a revision from another project
- Invalid project status transition
- Attempt to change project_number or project status via PATCH

Return clear errors.

Do not expose raw database exceptions to the frontend.

============================================================
17. AUDITABILITY
============================================================

Preserve created_at / updated_at on projects and revisions.

Phase 0 did not establish an audit log. Do not build one in this phase.

created_by stays nullable so a future users table and audit system can attach
identity without rewriting these tables.
