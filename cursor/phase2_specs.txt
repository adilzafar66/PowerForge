POWERFORGE — PHASE 2 IMPLEMENTATION
DOCUMENT MANAGEMENT, IMMUTABLE FILE STORAGE, AND REVISION INHERITANCE

Specification version: 2 (amended after review of v1 against the Phase 1 repository)

You are implementing Phase 2 of the PowerForge application.

PowerForge is an engineering software platform that will eventually ingest
electrical engineering documents, extract equipment and topology information
using AI, build a centralized engineering model, support engineer
verification, and later export that model to analysis tools such as ETAP,
SKM, and EasyPower.

DO NOT implement those future capabilities in this phase.

This phase is strictly about creating a robust document-management and
revision-inheritance foundation.

The current repository state after Phase 1 is the source of truth. Where this
specification and the repository disagree, follow the repository for naming
and conventions, and follow this specification for behavior. If a conflict
affects behavior, stop and report it rather than guessing.

0. AMENDMENTS IN THIS VERSION (REVIEW SUMMARY)
======================================================================

Version 1 contained gaps and contradictions. They are resolved as follows
(details are in the referenced sections):

 1. Cross-project lineage was claimed to be DB-enforced but a plain FK cannot
    do that. Now: composite foreign keys + CHECK constraints (sections 5, 8, 24).
 2. Phase 1 maps ANY IntegrityError to DuplicateRevisionIdentifier. With new
    FKs/uniques this would produce wrong errors. Now: map by constraint name
    (section 23).
 3. The unscoped download route could not satisfy the cross-project rule.
    Now: download URLs are issued only through the revision-document route
    (section 21).
 4. Presigned URLs break in docker (internal MinIO hostname). Now: separate
    public endpoint setting (section 29).
 5. "No base revision" could not be expressed when an ACTIVE revision exists.
    Now: omitted vs explicit-null semantics, tri-state carry-forward
    (section 6).
 6. Interaction with the existing `activate` flag is now defined (section 6).
 7. Lineage is immutable after creation (section 5).
 8. There was no way to reuse an existing Document in a revision that started
    empty. Now: "reuse document from another revision" operation (section 21).
 9. Added concurrency/locking rules (section 18) and snapshot semantics
    (section 19).
10. Tightened file validation (extension/content agreement, image pixel cap,
    filename sanitization, empty files, safe serving) (section 13).
11. Added put-if-absent object immutability and listed orphan-object debt
    (sections 10, 40).
12. The repository already has `packages/document-model`; Phase 2 extends it
    instead of creating `packages/document` (section 22).

======================================================================
2. PHASE 2 GOAL
======================================================================

Implement document management for engineering project revisions.

At the end of Phase 2, a user must be able to:

- open a project revision
- upload engineering PDFs and images (one or many through the UI)
- store original files in object storage as immutable bytes
- view revision documents
- manually classify documents
- edit revision-scoped document metadata
- download/view original files
- remove a document from the current revision without deleting the file
- restore a removed document
- create a new revision based on another revision
- automatically carry forward the base revision's document package
- distinguish inherited documents from newly uploaded documents
- replace a document in a new revision without affecting the previous one
- reuse an existing project document in another revision without re-uploading
- preserve historical revision document packages
- be prevented from changing superseded revisions

Core engineering behavior:

    Revision N+1 is usually built on Revision N.
    A new revision therefore normally inherits the base revision's documents.

    FILES MUST NOT BE PHYSICALLY COPIED WHEN A REVISION IS CREATED.
    Inheritance copies database associations only.

======================================================================
3. ARCHITECTURAL PRINCIPLES
======================================================================

Long-term conceptual pipeline:

    Documents -> Evidence -> Extraction Candidates -> Engineering Model
              -> Engineer Verification

Phase 2 implements only the document foundation. AI output must never become
part of the document domain. Original engineering files are evidence and
remain immutable.

Mandatory data model. Two distinct concepts:

    DOCUMENT
        An immutable uploaded file artifact.

    REVISION DOCUMENT
        The inclusion and interpretation of that artifact within one
        particular revision.

    Project
      ├── ProjectRevision (Rev 0)
      │      └── RevisionDocument ──┐
      │                             ├──► Document ──► immutable stored object
      └── ProjectRevision (Rev 1)   │
             └── RevisionDocument ──┘   (same Document, new association row)

DO NOT model Document as belonging exclusively to one revision.

Example. Revision 1: SLD_RevA, Transformer_T1, Utility_Fault_Data.
Revision 2 is created based on Revision 1 and initially contains the same
three (inherited). SLD_RevB arrives. Revision 2 becomes: SLD_RevA REMOVED,
SLD_RevB INCLUDED/UPLOADED, Transformer_T1 and Utility_Fault_Data
INCLUDED/INHERITED. Revision 1 is unchanged. This is copy-on-write
revisioning. No object-storage copies are created.

Revision-scoped metadata lives on RevisionDocument, never on Document, so
Revision 1 stays historically frozen even if Revision 2 later classifies or
describes the same Document differently.

5. REVISION LINEAGE
======================================================================

Add to ProjectRevision:

    based_on_revision_id   nullable UUID

Meaning: "this revision was created based on that revision."

Rules:

- The base must belong to the SAME project. It may be any status, including
  SUPERSEDED. It need not be ACTIVE.
- A revision cannot be based on itself.
- Lineage is IMMUTABLE after creation. RevisionUpdate must not accept
  based_on_revision_id. Because lineage is set only at creation, when a
  revision has no descendants, cycles are impossible by construction.
- Activation behavior is unchanged from Phase 1 (including the rule that only
  revisions created after the current ACTIVE revision can be activated).
  Activating a revision supersedes the current ACTIVE revision regardless of
  lineage.

Database enforcement (not just service-level):

- project_revisions gets UNIQUE (project_id, id)
  [uq_project_revisions_project_id_id], used as a composite FK target.
- Composite FK (project_id, based_on_revision_id)
  -> project_revisions (project_id, id)  [fk_project_revisions_based_on].
  With nullable based_on_revision_id the FK is skipped when it is NULL.
  This makes cross-project lineage impossible at the database level.
- CHECK (based_on_revision_id IS NULL OR based_on_revision_id <> id)
  [ck_project_revisions_based_on_not_self].
- No ON DELETE CASCADE anywhere in Phase 2. Revisions and documents are never
  deleted.

The service layer ALSO validates and raises InvalidBaseRevision (or the
repository's equivalent not-found error for a base id from another project)
so users get clean errors instead of constraint failures.

Revision responses include based_on_revision_id and the base's identifier.

6. REVISION CREATION BEHAVIOR
======================================================================

Extend the existing revision-creation API and UI. Request fields:

    identifier                (existing)
    description               (existing)
    activate                  (existing Phase 1 flag; keep working)
    based_on_revision_id      UUID | null | omitted   (three distinct states)
    carry_forward_documents   bool | null | omitted

The schema must distinguish omitted from explicit null (use
model_fields_set or equivalent).

Base resolution:

  A. based_on_revision_id = UUID:
     verify it belongs to the same project; use it.
  B. based_on_revision_id omitted:
     use the project's current ACTIVE revision if one exists; otherwise
     no base (NULL).
  C. based_on_revision_id explicitly null:
     NO base, even if an ACTIVE revision exists. Lineage is NULL.

Carry-forward resolution:

  D. carry_forward_documents omitted or null:
     true if a base was resolved, otherwise false.
  E. carry_forward_documents = true with no resolved base:
     reject with InvalidBaseRevision.
  F. carry_forward_documents = false:
     no documents are inherited. The base (if any) is still recorded.

Inheritance (when carry-forward resolves to true):

  - copy every RevisionDocument of the base with status INCLUDED
  - never copy REMOVED associations
  - never copy file bytes or touch object storage
  - each copy points to the SAME Document
  - origin = INHERITED, status = INCLUDED
  - inherited_from_revision_id = base revision id
  - copy revision-scoped metadata: document_type, document_number,
    description, notes
  - do NOT copy: RevisionDocument.id, added_at, added_by, removed_at,
    removed_by (set new timestamps normally)
  - if the base itself contains INHERITED associations, the copies still
    reference the BASE revision as inherited_from_revision_id (one hop of
    provenance; the Document identity gives the full history)

Atomicity and ordering (single transaction):

  1. lock the project row (existing _get_project_for_write(for_update=True))
     when activate is true OR a base is being resolved
  2. lock the BASE revision row FOR UPDATE so its package cannot change
     mid-copy (lock order is always project -> revision)
  3. create the revision and flush
  4. insert inherited RevisionDocument rows
  5. if activate is true, run the existing activation logic (this may
     supersede the base). Documents are copied BEFORE activation so the
     base's package is read while it is still in its pre-activation state.
  6. commit once

If any step fails, nothing is persisted; the new revision must not exist
partially. Response includes inherited_document_count.

Phase 1 activation behavior and the one-ACTIVE-per-project invariant must
continue to work.

======================================================================
7. DOCUMENT ENTITY
======================================================================

Document represents the immutable uploaded artifact.

    id                UUID primary key (generated by the service before
                      upload so the storage key can use it)
    project_id        UUID FK -> projects.id, NOT NULL
    original_filename text NOT NULL (sanitized basename, section 13)
    storage_key       text NOT NULL, UNIQUE
    mime_type         text NOT NULL (derived from detected content, never
                      from the browser)
    file_extension    text NOT NULL (lowercase, leading dot, e.g. ".pdf")
    size_bytes        bigint NOT NULL, CHECK > 0
    sha256            text NOT NULL (lowercase hex)
    uploaded_at       timestamptz NOT NULL
    uploaded_by       nullable UUID (matches created_by convention; auth is
                      deferred)

Additional constraints:

- UNIQUE (project_id, id) [uq_documents_project_id_id] as a composite FK
  target (section 8).
- Index on project_id; index on (project_id, sha256) for duplicate detection.

Rules:

- No revision id on Document. No file bytes in PostgreSQL.
- SHA-256 is NOT unique. Identical content may legitimately exist as
  separate Documents. The hash is for integrity and duplicate detection,
  not deduplication.
- project_id, original_filename, storage_key, mime_type, file_extension,
  size_bytes, sha256, uploaded_at, uploaded_by are IMMUTABLE after creation.
  Expose no API that changes them or replaces the stored file.

8. REVISION DOCUMENT ENTITY
======================================================================

    id                          UUID primary key
    project_id                  UUID NOT NULL  (intentional denormalization,
                                see below)
    revision_id                 UUID NOT NULL
    document_id                 UUID NOT NULL
    origin                      enum UPLOADED | INHERITED
    inherited_from_revision_id  nullable UUID
    status                      enum INCLUDED | REMOVED
    document_type               enum (section 9), default UNKNOWN
    document_number             nullable text
    description                 nullable text
    notes                       nullable text
    added_at                    timestamptz NOT NULL
    added_by                    nullable UUID
    removed_at                  nullable timestamptz
    removed_by                  nullable UUID

Constraints:

- UNIQUE (revision_id, document_id) [uq_revision_documents_revision_id_document_id].
  A Document appears at most once in a revision.
- Composite FKs guarantee that revision, document, and inheritance source all
  belong to the same project at the database level:
    (project_id, revision_id)                -> project_revisions (project_id, id)
    (project_id, document_id)                -> documents (project_id, id)
    (project_id, inherited_from_revision_id) -> project_revisions (project_id, id)
  project_id on RevisionDocument is deliberately denormalized to make these
  FKs possible. The service sets it from the revision and never accepts it
  from the client.
- CHECK (origin = 'INHERITED') = (inherited_from_revision_id IS NOT NULL)
- CHECK inherited_from_revision_id IS NULL OR inherited_from_revision_id <> revision_id
- CHECK (status = 'REMOVED') = (removed_at IS NOT NULL)
- Indexes: revision_id, document_id, (revision_id, status),
  (revision_id, document_type). Do not over-index.

Note: when the same Document is reused via "reuse" (section 21) the origin is
INHERITED and inherited_from_revision_id is the source revision.

10. OBJECT STORAGE
======================================================================

Files live in S3-compatible object storage (MinIO in development). Domain and
service code must depend on an abstraction, never on the S3/MinIO SDK.

Define an ObjectStorage interface (Protocol/ABC) in
powerforge_api/storage/ with behavior equivalent to:

    ensure_bucket()
    put(key, fileobj, size, content_type)   -> never overwrites an existing key
    get(key)                                -> readable stream
    exists(key)                             -> bool
    delete(key)
    create_download_url(key, filename, content_type, disposition, expires_seconds)

Implementations:

- S3ObjectStorage using boto3 (S3 API; works with MinIO, AWS S3, and other
  S3-compatible services; matches the existing S3_* settings). Use SigV4 and
  path-style addressing for MinIO.
- InMemoryObjectStorage (fake) for tests, with injectable failures.

Immutability:

- put() must refuse to overwrite an existing key (use conditional put such as
  If-None-Match where supported, or an exists() check as fallback; the fake
  raises). Keys contain a fresh UUID so collisions are not expected; this is
  a safety net.
- Bucket versioning is recommended for production deployments and documented,
  but not required in development.

Objects are never public. No anonymous bucket policy. Verify that
minio-init does not set one.

The storage instance is provided through a FastAPI dependency
(get_object_storage) that tests can override.

13. FILE VALIDATION
======================================================================

Supported: PDF (.pdf), PNG (.png), JPEG (.jpg, .jpeg), TIFF (.tif, .tiff).

Validate extension AND actual content. Never trust the browser Content-Type.
Never store it.

Checks, in order:

 1. Filename: reduce to basename (strip any path components), remove control
    characters, trim, max 255 characters, must be non-empty. The result is
    stored as original_filename. It is never used in storage keys.
 2. Extension: lowercase; must be in the allow-list, else
    UnsupportedDocumentType.
 3. Size: must be > 0 and <= MAX_UPLOAD_BYTES (enforced while streaming; a
    Content-Length header is only an early-reject optimization, never
    trusted). Else FileTooLarge. Empty file -> InvalidFileContent.
 4. Content detection:
    - PDF: header "%PDF-" within the first 1024 bytes.
    - Images: open with Pillow (Image.open + verify()). Phase 2 validates
      structure and header; full pixel decoding is deferred to Phase 3.
      Set the pixel cap explicitly: reject if width*height exceeds
      MAX_IMAGE_PIXELS (configurable, default 600,000,000 to allow large
      engineering scans) by checking dimensions from the header BEFORE any
      decode. Treat PIL.Image.DecompressionBombError as InvalidFileContent.
      Multi-page TIFFs are accepted; pages are not inspected.
 5. Agreement: the detected format must match the extension family
    (PNG<->.png, JPEG<->.jpg/.jpeg, TIFF<->.tif/.tiff, PDF<->.pdf).
    A JPEG named .png is rejected with InvalidFileContent.
 6. mime_type is derived from the detected format
    (application/pdf, image/png, image/jpeg, image/tiff).

Reject executables, renamed arbitrary files, and unsupported formats.

Layering: pure rules (allow-list, extension normalization, filename
sanitization, PDF header check, extension<->format agreement, storage-key
builder) live in the document domain package. Pillow-based image inspection
lives in the API service layer (FileInspector), not the domain package.

Known limitation (record as technical debt): a header check does not detect
PDF/other polyglot files. This is acceptable because Phase 2 never renders or
executes uploaded files server-side and serves them with the stored
content type from the storage domain (section 21).

======================================================================
14. FILE SIZE AND STREAMING
======================================================================

    MAX_UPLOAD_BYTES   default 262144000 (250 MB), configurable.

Never read a whole upload into RAM. Use the framework's spooled temporary
file, pass a binary file-like object plus filename to DocumentService (the
service must not import FastAPI types), compute SHA-256 and size in a single
streaming pass, then validate, then stream the same file to object storage.
Remind operators (docs) that reverse proxies must also allow the configured
body size.

======================================================================
15. UPLOAD FLOW
======================================================================

Each API request uploads exactly ONE file. The frontend may select many
files and upload them individually (isolated failures, clean retries,
per-file progress, simple consistency).

Backend flow:

    Request
      -> Validate project exists            (read, no lock)
      -> Validate revision belongs to project
      -> Early mutability check             (cheap fast-fail; re-checked later)
      -> Stream file: enforce size, compute SHA-256, spool to temp file
      -> Validate content (section 13)
      -> Generate Document UUID and storage key
      -> put() object to storage            (NO locks held during this step)
      -> Open DB transaction; lock the revision row FOR UPDATE;
         RE-CHECK project and revision mutability under the lock
         (guards against a concurrent activation superseding the revision)
      -> Detect duplicates (same project_id + sha256)
      -> Insert Document
      -> Insert RevisionDocument(origin=UPLOADED, status=INCLUDED, metadata)
      -> Commit
      -> Return metadata + duplicate info

Failure handling:

- Storage upload fails: create no database records; raise StorageUploadFailed
  (never expose raw SDK messages).
- Mutability re-check or database step fails after the object was stored:
  attempt best-effort deletion of the new object; log cleanup failures
  clearly. Do not leave a database record pointing to a nonexistent object.
- A crash between put() and commit can leave an orphaned object. Accept this
  and record it as technical debt (no GC in Phase 2).

======================================================================
16. DUPLICATE FILE BEHAVIOR
======================================================================

Detect identical content by SHA-256 across ALL Documents of the same project
(including Documents whose associations are all REMOVED).

- DO NOT reject. DO NOT deduplicate. DO NOT make SHA-256 unique.
- Accept the upload and return duplicate_detected = true and
  duplicate_document_ids = [...].
- The new upload is a NEW Document. Never reuse another Document based on
  hash alone.
- Frontend shows a non-blocking warning: "An identical file already exists
  in this project."

Intentional reuse (inheritance, section 6, or "reuse", section 21) is
different: it points a new association at the SAME Document by explicit
user/system action.

======================================================================
17. REVISION AND PROJECT MUTABILITY RULES
======================================================================

Document mutation = upload, reuse, metadata edit, remove, restore.

Allowed only when ALL are true:

    project status is ACTIVE or PAUSED
        (verified against Phase 1: _get_project_for_write blocks only
         ARCHIVED and CANCELLED, so PAUSED is editable; reuse that logic,
         the existing ArchivedProject and CancelledProject errors, and do
         not duplicate the rule)
    revision status is DRAFT or ACTIVE

Rejected:

    ARCHIVED project            -> ArchivedProject (existing)
    CANCELLED project           -> CancelledProject (existing)
    SUPERSEDED revision         -> RevisionReadOnly (new)

Reads are ALWAYS allowed regardless of status: list, get, and download for
superseded revisions and for archived/cancelled projects.

Scope of "frozen": a superseded revision's DOCUMENT PACKAGE is read-only.
Phase 1 revision metadata editing (identifier, description) is unchanged and
out of scope; the ADR must state this explicitly.

Backend enforcement is mandatory. Frontend disabling is not enforcement.

======================================================================
18. CONCURRENCY RULES
======================================================================

Lock order is always: project row -> revision row(s). Never the reverse.

- Document mutations lock ONLY the target revision row (SELECT ... FOR
  UPDATE) for the short database phase and re-check mutability after
  acquiring the lock. Streaming and object upload happen before the lock.
- Revision activation already locks the project row and then updates revision
  rows, so it naturally waits for in-flight document mutations on the
  revision being superseded, and subsequent mutations then see SUPERSEDED.
- Revision creation with a base locks the project row then the base revision
  row (section 6).

Concurrency tests may be best-effort, but the locking calls must exist and be
covered by at least one test that asserts the re-check-after-lock behavior
(for example by flipping revision status between the early check and the
locked re-check).

======================================================================
19. SNAPSHOT SEMANTICS (document in the ADR)
======================================================================

Inheritance is a SNAPSHOT at revision-creation time. Later changes to the
base revision's package (while it is still DRAFT/ACTIVE) are NOT propagated to
revisions created from it. Revision-scoped metadata is copied at creation
and diverges independently afterwards.

Because an ACTIVE revision's package remains editable, evidence attached to an
ACTIVE revision can change over time. Later phases that derive data from
documents must record the RevisionDocument/Document identity they used
(see docs/PROVENANCE.md update).

======================================================================
20. REMOVE AND RESTORE
======================================================================

Remove (while revision is mutable):
- never delete the Document row or the storage object
- status = REMOVED, removed_at = now, removed_by = user if available
- other revisions are unaffected
- removing an already REMOVED association is an idempotent no-op that does
  not change removed_at/removed_by

Restore (while revision is mutable):
- status = INCLUDED, removed_at = NULL, removed_by = NULL
- restoring an INCLUDED association is an idempotent no-op

Metadata edits on a REMOVED association are rejected (restore first) with a
conflict error.

======================================================================
21. API DESIGN
======================================================================

Follow current REST conventions. Never expose ORM models; use Pydantic
schemas. Business logic stays in services, not route handlers. PATCH and
form schemas must reject unknown fields (extra="forbid") so attempts to set
immutable fields fail validation.

All routes are scoped under /api/projects/{project_id}/revisions/{revision_id}.
There is NO unscoped /api/documents/{id} route; documents are always reached
through a revision-document association that is verified to belong to the
given revision and project.

LIST
    GET  .../documents
    Query: status=INCLUDED|REMOVED|ALL (default INCLUDED),
           document_type=, origin=, search=
    Search is case-insensitive over original_filename, document_number,
    description. Escape LIKE wildcards. Deterministic order (added_at,
    then filename). No pagination in Phase 2 (record as technical debt).

UPLOAD
    POST .../documents          multipart/form-data, ONE file field
    Optional form fields: document_type, document_number, description, notes
    Response (201): revision document + duplicate_detected +
    duplicate_document_ids

REUSE EXISTING DOCUMENT (add from another revision)
    POST .../documents/reuse
    Body: { source_revision_document_id, document_type?/number?/description?/
            notes? overrides optional }
    The source association must be INCLUDED and belong to a revision of the
    SAME project. Creates a RevisionDocument with origin = INHERITED,
    inherited_from_revision_id = source revision, copying the source's
    revision-scoped metadata unless overridden. If the Document is already
    associated with the target revision (INCLUDED or REMOVED) reject with a
    conflict (for REMOVED, the message says to restore it). Subject to
    mutability rules. Cross-project sources are rejected
    (CrossProjectDocumentAccess); the composite FKs are the DB-level backstop.

GET ONE
    GET  .../documents/{revision_document_id}

UPDATE METADATA
    PATCH .../documents/{revision_document_id}
    Editable: document_type, document_number, description, notes

REMOVE / RESTORE
    POST .../documents/{revision_document_id}/remove
    POST .../documents/{revision_document_id}/restore

DOWNLOAD / VIEW ORIGINAL
    GET  .../documents/{revision_document_id}/download-url
    Query: disposition=inline|attachment (default attachment)
    Response: { url, expires_at, filename }
    - Allowed for INCLUDED and REMOVED associations, in any revision/project
      status (read-only history).
    - Short-lived presigned URL; default validity 900 seconds, configurable.
    - Presigned parameters set Content-Disposition (with the sanitized
      original filename) and Content-Type from the stored mime_type, so the
      browser never sniffs content.
    - Large files are never proxied through FastAPI.
    - A revision_document_id that does not belong to the given revision and
      project returns not-found. Cross-project access is rejected.

Response schema for a revision document includes: id, revision_id, document
{id, original_filename, mime_type, file_extension, size_bytes, sha256,
uploaded_at}, origin, inherited_from_revision_id,
inherited_from_revision_identifier, status, document_type, document_number,
description, notes, added_at, removed_at.

Suggested HTTP mapping (follow the existing router's error-mapping style;
existing code maps not-found/mismatch to 404, conflicts to 409,
validation-type errors to 422):

    404  ProjectNotFound, RevisionNotFound, RevisionProjectMismatch,
         RevisionDocumentNotFound, CrossProjectDocumentAccess
    409  RevisionReadOnly, ArchivedProject, CancelledProject,
         DocumentAlreadyInRevision, edit of a REMOVED association
    413  FileTooLarge
    415  UnsupportedDocumentType
    422  InvalidFileContent, InvalidBaseRevision
    502  StorageUploadFailed

 1. Document is an immutable uploaded artifact.

13. Lineage is immutable and database-enforced via composite foreign keys;
    RevisionDocument.project_id is intentionally denormalized for that
    purpose.
14. Downloads are issued only through revision-scoped routes using
    short-lived presigned URLs against a browser-reachable endpoint.
15. Storage uses boto3 behind an ObjectStorage abstraction; put never
    overwrites.

    package becomes read-only (still listable and downloadable).
