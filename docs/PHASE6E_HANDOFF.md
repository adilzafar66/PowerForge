# Phase 6E handoff

M1–M5 are implemented for review. Phase 6E adds reusable native and OCR source preparation, conservative spatial layout, enhanced candidate extraction and an offline evaluation. Live-model accuracy and real-document coverage remain unmeasured. Phase 6F and 6G are pending.

## Deployment and operation

1. Build the API, extraction worker, source-enrichment worker and scheduler images. Apply Alembic head `0016_enriched_extraction` before deploying the updated services.
2. Run `docker compose run --rm source-enrichment-worker python -m extraction_worker.tesseract` to read the deployed engine identity. Set `ENRICHMENT_ENABLED=true` and use the actual identity in `ENRICHMENT_OCR_CONFIGURATION` for the API, source worker and scheduler. The worker image pins the Tesseract engine and English data. A build with different binary or language bytes has a different preparation identity.
3. Process the document, then start `source-layout-v1` for the selected pages. Use `force_ocr_pages` when a hybrid PDF page contains scanned content whose coverage is unknown. Inspect the preparation and layout results before choosing exact result pairs for extraction.
4. Choose `engineering-openai-enriched-v1` for prose or `tables-openai-enriched-v1` for tables. Run both separately when needed. The runs can reuse the same completed enrichment. Production model execution uses the existing explicit external-processing settings.
5. Read `/extraction/runs/{run_id}/sources` for exact bindings and producer identities. The evidence endpoint returns signed access to the cited recognized text and source image when available. Use extraction run history to see results from both profiles. The document summary shows the latest completed or partially completed extraction across profiles.

The [M2 handoff](PHASE6E_M2_HANDOFF.md) contains deployment and OCR eligibility details. The [M4 handoff](PHASE6E_M4_HANDOFF.md) has the exact API paths and request shape. The M4 review moved independent source and layout verification outside the publication locks. The atomic write rechecks its lease and pinned identities. Migration 0016 can be downgraded when only prior-format history exists. The downgrade guard protects existing v5/v6 history.

## Independent evaluation

Run `powerforge-eval-spatial` on the [versioned corpus](../evals/spatial/v1/corpus.json). The [evaluation README](../evals/spatial/README.md) explains artifact retention, exact comparison scopes and the command. The [reference report](../evals/spatial/v1/reference-report.json) contains every selected case, result, miss, metric, version and observed stage measurement. The authored PDF pages were rendered with Poppler and checked against the annotated layout. The separate OCR run used actual PyMuPDF 1.28.2 and Tesseract 5.3.0 with Leptonica 1.82.0 on Linux ARM64, Python 3.12.16 and Pillow 12.3.0.

- The six OCR-evaluation cases produced five OCR invocations that returned words. The hybrid default case required explicit selection and stayed in the gold denominator. CER was 120 edits over 326 gold characters and WER was 30 edits over 51 gold words. The exact geometry-matched tag, value and unit counts were 5/7, 5/10 and 4/9. Exact punctuation-bearing words were 0/4. The low-resolution breaker case and the default hybrid case contributed substantial misses.
- At the primary geometry thresholds, native words and lines matched 128/128 and 69/69. OCR words and lines matched 30/51 and 6/20. Preferred-source selection was 150/169 by recall and 150/172 by precision. Cross-source agreement/conflict scoring was 4/8 by recall and 4/15 by precision. The reading-order graph recovered 110/149 authored edges and emitted 113 edges.
- The detector matched 5/7 table regions and 5/7 complete partitions, with zero false supported partitions among five emitted partitions. It recovered 34/56 cell occurrences and 26/44 header edges. Three of five borderless schedules were outside the authored simple-layout assumptions. One of those three had a correct partition. One of the two missed schedules retained a matching unresolved region. The irregular four-column cable schedule and qualified utility schedule were misses. The ruled hierarchical schedule had a correct partition. These counts describe the authored challenge cases. Field prevalence remains unmeasured.
- On the exact 6D positioned PDF, the legacy native replay recovered four literal cells but mapped 0/2 claims because it could not prove their relationships. The enhanced replay supported all four cell occurrences and both header paths and mapped 2/2 claims. The legacy hybrid replay also mapped 2/2, with visual-reported relationships. On the paired rotated native and image-only nameplates, both 6C and enhanced prose recovered 2/2 claims per case. The image-only legacy citation was page-level. The enhanced result cited recognized text and a supported region.
- Across all 15 cases, the deterministic mock and converters produced 8/13 fully correct prose claims and 16/36 fully correct table claims. Exact typed value and unit correctness was 3/6 and 9/19. Association correctness was 3/7 and 12/21. The report retains 6/14 prose and 6/22 table outcomes as incorrect or unmatched and counts zero duplicates. The replay recovered 0/2 expected UNMAPPED table claims and 0/1 expected INVALID prose claims with the expected status and source support. The source-dependent mock omits some claims, so these totals combine source coverage, mock coverage and deterministic conversion.
- The separate numeric control changed one recognized value from the printed 690 V to 600 V. The partition stayed correct. Artifact evidence remained exact while printed-text agreement and typed value correctness each lost one claim. The mapped 0.6 kV value kept `printed_text_independently_verified=false`.

The reference run retained 1,659,341 source and derived bytes across its 15 cases. Detached source replay read 813,478 bytes. Mock responses and converted outputs added 266,825 bytes. Rendering, preparation, layout and detached replay totaled 2.66 s, 0.96 s, 0.16 s and 0.37 s of wall time respectively. Preparation used 333 ms of Python process CPU and 549 ms of child CPU. The five OCR invocations reported 575 ms elapsed in total. The OS reported a 177 MiB process RSS high-water mark. Rendering a selected page walks the document prefix through the Phase 3 iterator. The run uses in-memory object storage with a local file archive and excludes queue and remote-store latency. Provider tokens and cost are null.

## Verification and compatibility

- The initial Linux suite passed 2,084 cases and reproduced three known frozen 6C PNG byte failures. The final Linux suite passed 2,089 cases in 277.40 seconds with those three assertions explicitly deselected and zero skips. It used PostgreSQL 16.15, Redis 7.4.11, MinIO RELEASE.2025-09-07T16-13-09Z and disposable Celery workers. The complete host 6C evaluation module passed all 41 cases, including the three byte checks. The Linux PNG encoder used zlib 1.2.13 and the host used 1.3.1.zlib-ng. The frozen PNGs, hashes and expected reports were retained.
- The focused M5 evaluator and migration gate passed seven cases. It exercises the real OCR adapter, artifact byte retention, a repeated-value occurrence swap, missed OCR denominators and the injected numeric fault. A pending legacy 0013 probe was migrated through 0016, executed and read back with exact v1 text evidence. The prior 0015 data preservation, legacy v4 retry and guarded downgrade checks also pass.
- Six built wheels reproduce accepted v1–v6 profile and runtime identities, M1–M3 resources and both complete frozen reports. The new evaluator completed the positioned PDF comparison directly from the built worker wheel. The fresh migration, resolved Compose config, Ruff, changed-file formatting, dependency and whitespace checks passed.

## Scope for later review

The synthetic corpus is small. Native layout intentionally abstains on unsupported relationships and has limited recall on irregular borderless schedules. OCR confidence is an engine measurement. It cannot establish printed numeric correctness, and a mapped candidate still requires review where transcription matters. The input projection cap can reject dense schedules. Real-document coverage, live OpenAI accuracy, operational latency under production load, and cross-platform PNG byte reproducibility remain open. Phase 6F can guide users through the two backend operations and separate profile runs. Phase 6G can evaluate broader operational conditions and hardening.
