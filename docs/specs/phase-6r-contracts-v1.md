# Phase 6R v1 contracts and implementation handoff

Baseline `dea1ed3b9423dec9c1834672519e16c2853add49` on `codex/phase-6r-ai-first-redesign`. The [redesign specification](phase-6r-extraction-redesign.md) remains authoritative. The Python models in `powerforge_extraction.phase6r_contracts` define the structured wire shapes and envelope admission. The [TypeScript contract](phase-6r-api.ts) defines the API and Documents data boundary. The two provider response schemas are the corresponding Pydantic validation JSON Schemas. Provider-specific schema adaptation may remove unsupported constraint keywords from the submitted schema provided the original Pydantic parser enforces them on receipt.

## Execution boundary

- Build one immutable page projection after successful preparation and layout. Read the image from the pinned analysis-image artifact and verify digest, size and upright dimensions before provider admission. Both requests carry the same required `page.owner` object with `document_id`, `document_page_id`, `processing_run_id` and the 1-based `page_number`. Those fields enter the page-context hash and the audited attempt input. Build the expected owner from the authorized run and persisted page binding. Pass it separately to request validation, which compares it with the explicit owner and the layout owner. The layout contract also binds the preparation owner. The coordinator verifies the source digest, artifact ownership and bytes against the persisted binding before dispatch. Provider echoes are correlation checks only. Authorization and publication derive from the server-side binding and successful recognition result.
- Use the layout's reading order and exact preferred reading text. Include each reading even when it belongs to a table. Each reading's alternate texts follow the corresponding layout member order with the preferred member excluded. Local tables, cell/header links and geometry are spatial hints. Send the verified image alongside the JSON request. Both stages use the identical page-context hash.
- Use the existing canonical JSON and SHA-256 utilities for typed contract objects. Hash the actual stage request, projected catalog, profile, prompt and response schema versions. Hash the typed, admitted Call 1 result after envelope validation and preserve its original observation order. Persist the recognition attempt, its page binding, the result and its digest. Only that successful attempt can supply Call 2's prerequisite.
- Recognition receives the complete registry-owned equipment description catalog. Attribute extraction receives the union of attributes for recognized types on eligible observations, keyed by equipment type and attribute key. Legend-only observations retain their source classification but are ineligible attribute owners. Unknown types use null and remain visible. Reference, spare, future and proposed observations may own attributes stated in the source. The model must leave ownership null when the source does not support it.
- If successful recognition produces no eligible types, persist `NoEligibleAttributes` against the same upstream digest with zero provider calls. It counts toward page completion. A failed recognition leaves the attribute stage blocked. The runtime checks provider refusal and incomplete/truncated finish states before invoking the parser. Record overflow explicitly. No clipped result counts as success.
- v1 bounds are 128 equipment observations, 512 registry assertions, 16 secondary raw-unmapped assertions, 12 citations and eight qualifiers per assertion where applicable. The request JSON is capped at 2 MiB, the image at 12 MiB and 24 million pixels, and the response JSON at 512 KiB. Apply the smaller deployed provider limits and profile token/deadline budgets before dispatch. Preflight the actual encoded transport payload. Abort over-capacity pages explicitly. Retain existing operation admission limits and a maximum of 50 documents and 50 selected pages per document, subject to the configured operation-wide cap. These are v1 engineering limits to exercise in C, distinct from accuracy targets.
- Treat source and result content as untrusted. A malformed shape, duplicate local identifier, incorrect envelope identity or capacity failure rejects the stage. A syntactically valid but foreign reading, invalid visual bounds, quote mismatch or unknown owner is recoverable at the observation boundary. Keep its original assertion in the bounded stage result, with a diagnostic. Persist only valid reference links. Provider transport errors, malformed outputs and stale work use existing retry policy, deadlines and lease recovery.

## Field trace and validation

- Equipment local references identify observations within one recognition result. Store tag state and raw tag independently, preserve raw qualification and display the explicit qualification. A known type yields `MAPPED`, even without a readable tag. Null registry type yields `UNMAPPED`. No extracted candidate points to a canonical model entity.
- Attribute local references are unique across both Call 2 arrays. Resolve an asserted owner only against the successful recognition result for that page and run. A valid but uncertain owner stays linked with `UNCERTAIN`. An unknown, ineligible or missing owner becomes `UNASSIGNED` with null FK. Preserve the claimed local ref in stage diagnostics. If the model explicitly says `UNASSIGNED`, discard any owner link and record the inconsistency.
- Preserve the raw label, value, unit, qualifiers and form exactly. Keep enum proposals separate from source strings. Check enum membership using the applicable registry attribute. For boolean text accept only case-insensitive `true`, `false`, `yes` and `no` after trimming. Keep the original string. Do not use a source synonym table. Keep exact number/integer values as decimal strings in API responses.
- Map using the linked eligible equipment's type and its allowed attribute key. A raw-unmapped assertion, absent/invalid ownership, unknown key, missing/ambiguous dimensional unit or unrepresentable qualified value yields `UNMAPPED` with reason code `UNSUPPORTED_ATTRIBUTE`, `UNASSIGNED_OWNER`, `UNKNOWN_ATTRIBUTE_KEY`, `UNIT_MISSING_OR_AMBIGUOUS` or `UNREPRESENTABLE_VALUE_FORM` as applicable. Preserve ranges and multiple ratings intact. Units may come from a cited header on the same page. Require unit text support before converting a dimensional value. For a valid key and owner with supplied unsupported units or malformed scalar/enum/boolean values use `INVALID` with `INVALID_UNIT` or `INVALID_VALUE`. Once these conditions pass, call canonical normalization and store the normalized value beside the raw assertion. Source support and association indicators remain independent of the mapping state.
- Store one candidate per assertion. A repeated raw assertion from another occurrence receives a distinct ID. In D, flag disagreements among comparable mapped assertions under the same owner and key when normalized values differ and qualifiers agree. Keep alternatives, including distinct qualified assertions, available side by side. Never combine equipment by tag or use cross-page observations to assign attributes.
- Evidence roles originate in the model output. D resolves a reading ref in the exact pinned layout, then selects the pinned source member matching any supplied quote. Use bounded whitespace comparison for a quote attached to a reading. A quote-only citation uses exact matching in the pinned page's text artifacts. Count distinct source occurrences and accept only a unique occurrence, including when native and OCR disagree or yield multiple locations. Bound the search to 2 MiB of aggregate page text and at most 512 characters per quote. If that scope cannot be searched completely within bounds, record unresolved evidence. A foreign reading cannot fall back to a quote. Preserve independent fragments and zero-based Unicode code point ranges `[start,end)`. A resolved occurrence may have an empty regions array.
- Model regions are finite decimals in the normalized upright frame. D applies the existing `Region` bounds. Valid model regions are `VISUAL_REPORTED`, invalid regions become `UNRESOLVED` with `INVALID_VISUAL_REGION`. Missing, ambiguous, mismatched and foreign citations use `NO_CITATION`, `AMBIGUOUS_QUOTE`, `QUOTE_MISMATCH` or `UNKNOWN_READING`. Persist page context for unresolved evidence, without a fabricated quote or offset. A verified location supports review and does not change the engineering interpretation.

## Clean-install schema and publication

Use this single Alembic chain, with each new revision ID under the default 32-character version-column limit.

1. Retain the current chain through `0010_authoring_refinement`.
2. B creates `6r_0011_runtime` with run, logical work, attempt, stage-result and call/control tables. B adds `6r_0012_sources` with the active local preparation and layout tables and exact per-run page bindings. B adds `6r_0013_operations` with revision-scoped operation/selection/request tables. Each revision points to the preceding ID.
3. C adds `6r_0013c_admission` after `6r_0013_operations` for expiring previews and stage diagnostics. D adds `6r_0014_publication` after `6r_0013c_admission`, with candidate and evidence tables and atomic publication constraints. The only final head is `6r_0014_publication`. Remove the replaced `0011`–`0017` revisions as the new chain lands. Never stamp or upgrade a populated old installation onto this graph.

Logical rows and constraints for the migration authors:

- `extraction_runs` owns document, processing run, versioned profile and status. Runs have purpose `SOURCE_ENRICHMENT` or `EXTRACTION`. Local preparation and layout work share the lease infrastructure with the two AI work stages and cannot dispatch provider calls. Local artifacts retain their existing prepared/layout provenance.
- `run_source_enrichment_bindings` pins each run page to its exact preparation and layout IDs/digests and, through the preparation manifest, its immutable analysis image. Composite FKs and the binding guard require matching document, page and processing run and the exact layout-to-preparation reference. An operation may begin while local preparation is pending. The binding is inserted once, before AI work for that page.
- `extraction_work_units` stores attempts keyed by run, logical page/stage key and attempt number. Unique constraints allow one active claim and at most one successful attempt per logical key. `extraction_unit_execution` stores lease tokens and hard deadlines. Retry locks the run and attempts, checks expected attempt number and admission budget, then allocates the next attempt. Unknown provider outcomes require existing acknowledgement before reattempt. Cancellation and commit serialize on the same run/attempt lock.
- `extraction_stage_results` is immutable and unique by producing attempt. Use bounded JSONB and the typed digest. An attribute result or skip must FK to the same-run/same-page successful recognition result and exact digest. Result kind and provider call count distinguish skip from executed results. Persist call telemetry and bounded, access-controlled result diagnostics. No credentials or signed URLs are persisted in diagnostics. Keep results for the lifetime of their run/source dependencies.
- `extraction_candidates` includes run/page/attempt identity, kind and local ref with uniqueness per stage result. Separate proposed key, typed slots, registry type and original text. Check exactly one matching typed slot for a mapped attribute and none for other attributes. Enforce owner FK to an equipment candidate from the exact recognition result, never to a canonical ID. `extraction_evidence` belongs to one candidate and run/page/binding, with unique candidate ordinal, role, localization discriminator and variant-specific locator constraints. A resolved fragment must reference a pinned text artifact. A visual fragment references the pinned page image. An unresolved fragment carries page context only.
- `extraction_operations`, `extraction_operation_requests` and `extraction_operation_items` retain project/revision scope, consent, request-key uniqueness, preview identity and one run association per included document. Repeated matching requests return the same operation. A conflicting payload under the same key is rejected. Only the owner operation cancels work it started; shared reuse detaches the operation without cancelling unrelated work.

Verify artifacts outside the write transaction. Commit output, effective result marker and attempt status in one transaction after rechecking run status, lease ownership, input/prerequisite digests and cancellation. A stale or cancelled attempt cannot publish. Keep successful sibling pages and successful recognition after attribute failures. Roll up to partial completion when only some pages finish. Replace old extraction run/unit/output/publication/terminal/control/fence and enriched extraction guards with these 6R constraints. Preserve the useful ownership checks in `source_enrichment_guard` and `source_spatial_guard` against the new rows. Retire extracted tables, source groups, family columns, table-output FKs and legacy version predicates. Verify the new chain in a disposable fresh PostgreSQL environment during B/D. Rehearse the cutover and recovery procedure in F.

## API and Documents behavior

- Use the existing revision-scoped operation prefix. Keep `POST /sources`, `POST /preview`, `POST /`, `GET /`, `GET /{operation_id}`, `POST /{operation_id}/cancel` and `POST /{operation_id}/retry`. Bind preview to ordered selection, revision membership, policy, pin/reuse decisions and expiry. Revalidate on start with literal consent. The supported start path is operation creation. Retry names the revision-document and page, discriminating `PREPARATION`, the two AI stages and `RESUME`; AI retries use the attempt guard in the DTO.
- Keep document-scoped `GET /`, `GET /runs`, `GET /runs/{run_id}`, `GET /runs/{run_id}/sources`, `GET /runs/{run_id}/candidates`, `GET /evidence/{evidence_id}` and existing scoped run retry/cancel. Use cursor pagination with stable (created_at, id) history ordering. The unified candidate endpoint serves both levels of the existing source-group browser. Remove direct run start, table results, the legacy `GET /groups` route and profile selectors. Register status uses one operation and one selected run per document.
- Gate every request through project/revision membership and revision writeability where applicable. Resolve signed viewer links through the existing pinned-artifact authorization path. Return no storage keys. Use existing error conventions for invalid/foreign scope, read-only revisions, stale preview, conflicting idempotency keys, and unavailable artifacts. Cost requires measured usage plus versioned pricing and otherwise uses null.
- The wizard previews page selection, preparation and provider limits and obtains consent before starting. Show preparation, recognition and attribute progress, partial failures and actionable retry/cancel controls. Explain an eligibility skip using the stored outcome. History keeps the selected run stable during polling. Candidates show raw, proposal and normalized fields with provenance and independent ownership, mapping and localization indicators. Render exact highlight polygons only when source coordinates exist, model boxes as approximate, and unresolved or missing geometry with page context. Preserve deep links to the pinned run/page/candidate. Read-only revisions can browse and cannot start, retry or cancel.

### Two-level candidate browser

Both levels use the selected 6R run and its effective published candidates.

- `view=groups` returns compact group summaries with label, tag, registry type, matching page numbers and matching candidate count. An equipment group's ID is the persisted equipment candidate UUID and its members are that observation and attributes linked to it. A run-scoped `unassigned` bucket contains attributes with a null owner. A raw-unmapped attribute with a valid owner appears in that owner's group. The UI identity is the pair `(run_id, group_id)`, independent of filters, polling and attribute retries. A deliberate re-extraction creates new observation IDs. Repeated tags and occurrences remain separate.
- `view=members&group_id=...` returns the selected group header and one candidate page. The header can be returned with zero matching members so the browser can keep its selection after a filter change. An optional `candidate_id` supports direct selection by requiring membership in that run and group. A foreign or missing group or candidate returns the existing scoped not-found response. The default flat view retains candidate listing by equipment ID where needed.
- Both levels accept the same search and filters. Trim and case-fold a literal search term of up to 200 characters. Search candidate source descriptions, tags, keys, raw labels, values and units, plus the owning equipment's tag and description. Apply page ID, equipment type, mapping status and candidate kind conjunctively to the same member. The equipment type comes from the equipment observation or the linked owner. Unassigned members have no equipment type. List a group when at least one member matches and count only matching members. The member query uses the identical predicate, so a group hit always has a corresponding matching row.
- Default page size is 25 groups or 20 members, capped at 100. Order equipment groups by the owner's page number and ID, with the unassigned bucket last. Order members by page number and candidate ID. Return the filtered total and opaque next/previous cursors bound to the run, view, group and filters. Reset pagination on filter changes. Use a set-based query over scoped candidates and their owner links, aggregating only for group summaries. Index run/page, run/owner and stable ordering keys, and keep evidence bodies and member payloads out of group listings. Grouping is a read projection over existing candidate relationships. It adds no persisted source-group object.

## Deferred acceptance cases

6R-A verifies wire admission and preserves recoverable assertions for later processing. Verify these outcomes when the corresponding runtime, publication and API paths are available.

- B rejects an artifact or text representation owned by a different document, processing run or page even when the submitted digest and request owner appear consistent. Reusing a reading alias or equipment local reference from another page cannot establish ownership.
- D retains an assertion with an unknown, cross-page or ineligible equipment reference and publishes it as `UNASSIGNED` with a null owner FK and a diagnostic. The database rejects any direct write linking an attribute to equipment from a different page, run or recognition result.
- D publishes an unsupported key under a valid owner as `UNMAPPED` with `UNKNOWN_ATTRIBUTE_KEY`. A disallowed enum proposal under a valid enum key and owner is `INVALID` with `INVALID_VALUE`. In both cases preserve the raw assertion and proposal.
- D leaves a dimensional scalar without a source-supported unit `UNMAPPED` with `UNIT_MISSING_OR_AMBIGUOUS`. A supported cited header establishes a unit for the corresponding scalar. An unrepresentable range or qualified assertion preserves its raw value and qualifiers, has no normalized scalar and uses `UNREPRESENTABLE_VALUE_FORM` when its unit is otherwise established.
- D resolves a repeated quote such as `600` to `UNRESOLVED` with `AMBIGUOUS_QUOTE` and no precise highlight. A valid reading citation selects the exact occurrence. A foreign reading reference with the same quote still fails reference validation.
- D/E list distinct groups for repeated tags, surface the unassigned bucket, and prove group summaries and member pages agree under shared filters and search. Test stable group selection across retries and polling, next/previous pagination without duplicate rows for a stable result set, and denial of foreign group, candidate and cursor requests.

## Cutover runbook outline

1. Identify exact environment, host, database and isolation boundary. Obtain target-specific reset authorization and separately scope any artifact or queue cleanup. Verify the new migration head and application smoke tests in disposable infrastructure first.
2. Record the old release and target, stop all API/worker/scheduler writers, and take the authorized external backup if required. Verify the backup can restore with the old release. Disable stale worker credentials/consumers before resuming services.
3. Recreate the full designated database and its migration state. Apply the new clean-install chain and explicitly approved bootstrap records. Re-upload or reseed only approved documents. Do not restore legacy rows into 6R or flush shared stores.
4. Check schema/queue scope, absence of old extraction objects and routes, source ownership, and a fresh Documents workflow. Reopen traffic after smoke acceptance. If rollback is required, restore the compatible old release and full authorized backup together. Without that backup, use a fresh 6R database and forward repair.
