POWERFORGE — PHASE 4 IMPLEMENTATION
AI DOCUMENT CLASSIFICATION

You are implementing Phase 4 of PowerForge.

Phase 0 established the repository/application architecture.
Phase 1 implemented projects and project revisions.
Phase 2 implemented immutable Documents, RevisionDocument associations,
revision inheritance, manual document classification, and object storage.
Phase 3 implemented asynchronous Document processing, stable DocumentPages,
analysis/thumbnail/native-text artifacts, processing versioning, and the
document page viewer.

Phase 4 introduces the first semantic AI capability:

    AI-assisted document classification.

The purpose of Phase 4 is to determine:

    "What kind of engineering document is this?"

and, where appropriate:

    "What kind of engineering content is on each page?"

Phase 4 MUST NOT extract equipment, ratings, attributes, tables, electrical
connections, SLD topology, or engineering-model entities.

======================================================================
2. PHASE 4 GOAL
======================================================================

After Phase 4:

- a successfully processed Document can be automatically classified by AI
- classification belongs to the immutable Document, not RevisionDocument
- classification is reused when the same Document is inherited into another
  project revision
- AI classifications are persisted as immutable suggestions
- AI suggestions NEVER silently change RevisionDocument.document_type
- an engineer can explicitly accept an AI document-level suggestion
- an engineer can continue to classify documents manually
- mixed-document PDFs are supported
- mixed/uncertain documents can receive page-level AI classifications
- AI results are provider/model/prompt/taxonomy/profile versioned
- classification can be disabled without affecting document workflows
- existing processed Documents can be backfilled
- reclassification creates new classification history rather than replacing
  previous results
- AI usage telemetry is captured
- an evaluation harness exists to measure actual classifier quality

3. CORE AUTHORITY MODEL
======================================================================

This distinction is mandatory:

    AI classification prediction
            !=
    confirmed revision document type

The existing field:

    RevisionDocument.document_type

remains the engineer-facing authoritative classification for that revision.

AI results are suggestions.

Example:

    RevisionDocument.document_type
        UNKNOWN

    AI prediction
        TRANSFORMER_SHOP_DRAWING
        confidence = HIGH

The UI may show:

    AI suggestion:
    Transformer Shop Drawing

    [ Accept ]
    [ Choose another type ]

Only explicit acceptance changes RevisionDocument.document_type.

Never implement:

    confidence > threshold
        → automatically overwrite document_type

There is NO automatic acceptance in Phase 4.

4. CLASSIFICATION BELONGS TO DOCUMENT
======================================================================

Machine classification belongs to the immutable Document.

Correct:

    RevisionDocument ─┐
    RevisionDocument ─┼────► Document
    RevisionDocument ─┘         │
                                ▼
                    DocumentClassificationRun
                                │
                                ▼
                    ClassificationPredictions

Incorrect:

    Revision 0 → independent AI classification
    Revision 1 → duplicate AI classification
    Revision 2 → duplicate AI classification

If the same Document is inherited or reused across revisions, its machine
classification is reused.

Human acceptance remains revision-scoped because
RevisionDocument.document_type is revision-scoped.

5. DOCUMENT CLASSIFICATION TAXONOMY
======================================================================

Preserve the existing DocumentClassification taxonomy and add:

    MIXED_DOCUMENT

The resulting taxonomy must include:

    UNKNOWN
    SINGLE_LINE_DIAGRAM
    ELECTRICAL_DRAWING
    PANEL_SCHEDULE
    EQUIPMENT_SCHEDULE
    CABLE_SCHEDULE
    TRANSFORMER_SHOP_DRAWING
    SWITCHGEAR_SHOP_DRAWING
    BREAKER_DOCUMENT
    MOTOR_DATA
    FAULT_DATA
    SPECIFICATION
    EQUIPMENT_PHOTO
    NAMEPLATE_PHOTO
    STUDY_DOCUMENT
    OTHER
    MIXED_DOCUMENT

Do not redesign the rest of the taxonomy in Phase 4.

Version this taxonomy explicitly, for example:

    document-taxonomy-v2

Definitions must live in version-controlled source and be available to the
classifier prompt.

Important semantics:

UNKNOWN
    There is not enough evidence to confidently determine the class.

OTHER
    There is enough evidence to understand the document, but no defined class
    fits it well.

MIXED_DOCUMENT
    The document contains multiple substantive sections belonging to different
    taxonomy classes.

Do NOT classify a document as MIXED_DOCUMENT merely because it contains:

    cover page
    title page
    table of contents
    general notes

plus one substantive document type.

Example:

    cover
    contents
    transformer drawings
    transformer data

should normally still be:

    TRANSFORMER_SHOP_DRAWING

But:

    switchgear drawings
    breaker datasheets
    relay documentation
    unrelated equipment schedules

may legitimately be:

    MIXED_DOCUMENT

======================================================================
6. DOCUMENT-LEVEL VS PAGE-LEVEL CLASSIFICATION
======================================================================

Primary classification is DOCUMENT-level.

Every AI classification run first classifies the entire Document.

Conditional PAGE-level classification follows only when the document-level
result is mixed or uncertain.

Run page classification when ANY of the following are true:

    predicted_type == MIXED_DOCUMENT

    predicted_type == UNKNOWN

    document confidence score < configured HIGH-confidence threshold

Default initial confidence thresholds:

    HIGH:
        >= 0.85

    MEDIUM:
        >= 0.60 and < 0.85

    LOW:
        < 0.60

These are routing heuristics, NOT calibrated statistical probabilities.

Store the numeric classifier score, but the normal UI should primarily display:

    HIGH
    MEDIUM
    LOW

Page-level classifications use the same taxonomy EXCEPT:

    MIXED_DOCUMENT is NOT valid as a page classification.

A page that cannot be confidently classified should use UNKNOWN.

======================================================================
7. PAGE CLASSIFICATION IS A ROUTING SUGGESTION
======================================================================

Do NOT introduce an authoritative human-confirmed page-type model in Phase 4.

Page predictions are AI suggestions that future extraction phases may use for
routing.

They are visible to the engineer, but Phase 4 does NOT require the engineer to
approve every page individually.

Do NOT add:

    DocumentPage.confirmed_type

or revision-specific page classification tables in this phase.

The document-level classification remains the only classification promoted to
RevisionDocument.document_type through explicit engineer acceptance.

9. PHASE 3 PROCESSING DEPENDENCY
======================================================================

Classification requires a COMPLETED Phase 3 DocumentProcessingRun.

Every DocumentClassificationRun must reference the exact:

    processing_run_id

whose artifacts were used.

Do NOT classify:

    PENDING
    RUNNING
    FAILED

processing output.

Only consume artifacts belonging to a fully COMPLETED Phase 3 run.

The run to classify is the current run for the active processing target:

    (document_id, processor_version, profile_hash)

as Phase 3 already selects it, and only when that run is COMPLETED.

A document may also have older COMPLETED runs for a previous processor version
or profile hash. Leave those unclassified while a newer current run exists.
If the current run is not COMPLETED, do not classify.

The page set for that run is the DocumentPage rows of that document with
page_number from 1 through that run's pages_total. That is the same set Phase 3
requires before it marks the processing run COMPLETED.

Leave DocumentPage rows with a higher page_number out of classification. Those
rows can remain after a later processing profile produced a shorter page list.

Native text comes from that run's NATIVE_TEXT PageArtifact. Thumbnail bytes
come from that run's THUMBNAIL PageArtifact. DocumentPage.native_text_char_count
is updated in place and can reflect a different run, so it is not the text
source.

A page in this set with no THUMBNAIL artifact on the referenced run fails the
classification run as ARTIFACT_UNAVAILABLE.

This creates reproducibility:

    classifier output
        ↓
    exact processing run
        ↓
    exact DocumentPages/PageArtifacts
        ↓
    immutable Document

======================================================================
11. RUN IDEMPOTENCY
======================================================================

For one classifier identity:

- at most one PENDING/RUNNING run may exist
- multiple historical FAILED runs are allowed
- multiple historical COMPLETED runs are allowed when explicit reclassification
  is requested

Enforce the live-run rule with a partial unique index on the classifier
identity hash:

    WHERE status IN ('PENDING', 'RUNNING')

COMPLETED and FAILED stay out of that index. This is deliberately different
from Phase 3's uq_document_processing_runs_one_live, which treats COMPLETED as
the single live row. Copying that index would reject an explicit reclassify.

A different classifier identity, such as a new prompt or model version, may
have its own PENDING or RUNNING run while an older identity is still in flight.

ensure_document_classification(...):

If compatible COMPLETED exists:
    return the latest compatible completed run
    do not spend AI tokens again

If compatible RUNNING exists:
    return it

If compatible PENDING exists:
    safely re-enqueue that same unclaimed run if requested through the
    ensure/backfill path
    return it

If only FAILED runs exist:
    do NOT retry automatically
    require explicit retry

Explicit retry:

    Allowed only when the target run is FAILED and it is the newest run for
    that classifier identity.

    FAILED Run 1
        ↓
    create PENDING Run 2
        retry_of_run_id = Run 1

    If a PENDING or RUNNING run already exists for that identity, insert
    nothing. Return 409 classification_in_progress and the in-flight run id.

    If a newer run of any status already exists for that identity, insert
    nothing. Return 409 classification_not_retryable.

Explicit reclassification:

    uses the current configured classifier identity
    may create a new PENDING run even when a compatible COMPLETED run exists

    If that identity already has a PENDING or RUNNING run, insert nothing.
    Return 409 classification_in_progress and the in-flight run id.

ensure and backfill still return an in-flight run, re-enqueue only an
unclaimed PENDING run, and do not retry FAILED runs.

Do not overwrite or mutate historical predictions.

======================================================================
12. ATOMIC WORKER CLAIM
======================================================================

Classification workers must atomically claim:

    PENDING → RUNNING

Only one delivery may successfully claim a run.

Duplicate Celery delivery must therefore be harmless.

A duplicate task seeing:

    RUNNING
    COMPLETED
    FAILED

must not independently perform another provider call for that same run.

When the task hits its soft time limit, mark the run FAILED with
CLASSIFICATION_TASK_TIMEOUT and commit that status before the process exits.
Section 36 defines that code. A redelivered task then sees FAILED and must not
continue the provider calls.

15. HUMAN ACCEPTANCE PROVENANCE
======================================================================

Add to RevisionDocument:

    accepted_classification_prediction_id
        nullable FK

Meaning:

    "The current RevisionDocument.document_type was explicitly accepted from
     this AI document prediction."

Acceptance endpoint/service behavior:

1. prediction exists
2. prediction scope == DOCUMENT
3. prediction belongs to the SAME underlying Document
4. its classification run is COMPLETED
5. revision/project is allowed to mutate document metadata under existing
   lifecycle rules
6. set:

       RevisionDocument.document_type =
           prediction.predicted_type

       accepted_classification_prediction_id =
           prediction.id

A manually selected document type must:

    update document_type
    clear accepted_classification_prediction_id

Presence of document_type on the metadata request is the manual selection.
Clear the prediction id even when:

    the submitted type equals the stored document_type
    the submitted type equals the AI prediction

Skipping unchanged document_number, description, and notes stays as it is.
A patch that omits document_type leaves accepted_classification_prediction_id
unchanged.

Accept is the only operation that sets accepted_classification_prediction_id.

This avoids falsely claiming AI acceptance provenance.

17. REVISION INHERITANCE
======================================================================

Both existing metadata copy paths carry:

    accepted_classification_prediction_id

along with:

    document_type
    document_number
    description
    notes

The paths are:

    creating a project revision that carries included associations forward
    reusing a document into another revision of the same project

because the new association references the same immutable Document.

On reuse, a document_type override is a manual selection: write that type and
set accepted_classification_prediction_id to null. With no type override, copy

The new revision or association remains free to change or manually override
its classification.

Previous revisions remain unchanged.

25. CONFIDENCE SEMANTICS
======================================================================

Do not describe confidence_score as a calibrated probability.

It is:

    classifier confidence score used for ranking/routing.

Derive confidence_band deterministically in PowerForge:

    score >= 0.85:
        HIGH

    score >= 0.60:
        MEDIUM

    score < 0.60:
        LOW

Thresholds belong to the versioned classification profile.

Do not ask the model to independently return both score and band.

27. DETERMINISTIC PAGE SAMPLING
======================================================================

Document-level classification must not send every page of a large document.

Page count and sampling use the classification page set from section 9.
Native text for a sampled page is that processing run's NATIVE_TEXT artifact,
truncated to max_text_chars_per_page. A missing NATIVE_TEXT artifact means the
page has no native text.

For visual sampling:

If page_count <= document_image_sample_count:
    use every page

Otherwise:
    choose deterministically spaced pages including:
        first
        last
        evenly distributed interior pages

Do not use randomness.

For native-text sampling:

Select up to:

    document_text_sample_count

deterministically distributed pages.

Native text per page must be bounded by:

    max_text_chars_per_page

Normalize obvious whitespace only.

Do not perform semantic summarization before classification.

Do not include the current manually confirmed:

    RevisionDocument.document_type

in AI classifier input.

Otherwise the AI would be partially told the expected answer and evaluation
would be contaminated.

Process pages in deterministic bounded batches.

Suggested initial batch size:

    8 pages/provider call

For each page provide:

    page_number
    bounded native-text excerpt if available
    page thumbnail
    filename/document context

Use the page-classification schema:

    page_number
    predicted_type
    confidence_score
    alternatives
    rationale

The expected result must contain:

    exactly one result for every requested page
    no unknown page numbers
    no duplicate page numbers
    no MIXED_DOCUMENT page prediction

Any schema/page-set mismatch is an INVALID_PROVIDER_RESPONSE failure.

33. AUTOMATIC CLASSIFICATION TRIGGER
======================================================================

When Phase 3 successfully transitions a processing run to:

    COMPLETED

and:

    AI_CLASSIFICATION_ENABLED == true

enqueue classification for that Document and for the processing run that just
completed. That run is the current completed run from section 9.

Do NOT couple the Phase 3 document-processing package directly to OpenAI.

The document-worker enqueues classification only after the COMPLETED status is
committed. Its processing enqueue port stays a no-op during claim. Classification
enqueue publishes by task name through a port. That port does not import the
OpenAI SDK or extraction-worker modules.

If classification enqueue fails:

    Phase 3 processing remains COMPLETED

36. CLASSIFICATION FAILURE HANDLING
======================================================================

Represent clean classification errors equivalent to:

    AI_CLASSIFICATION_DISABLED
    PROVIDER_AUTH_ERROR
    PROVIDER_RATE_LIMITED
    PROVIDER_UNAVAILABLE
    PROVIDER_TIMEOUT
    CLASSIFICATION_TASK_TIMEOUT
    PROVIDER_REFUSAL
    INVALID_PROVIDER_RESPONSE
    CLASSIFICATION_INPUT_ERROR
    ARTIFACT_UNAVAILABLE
    UNKNOWN_CLASSIFICATION_ERROR

Keep these two timeouts distinct:

    One provider invocation exceeded AI_CLASSIFICATION_TIMEOUT_SECONDS
        → PROVIDER_TIMEOUT

    The Celery task exceeded AI_CLASSIFICATION_TASK_SOFT_TIME_LIMIT_SECONDS
        → CLASSIFICATION_TASK_TIMEOUT

PROVIDER_TIMEOUT means one call did not answer in time. That call may be the
document classification or one page batch.

CLASSIFICATION_TASK_TIMEOUT means the whole task exhausted the worker
allowance. The run may already contain many successful provider calls, for
example dozens of page batches of a long mixed document. On
SoftTimeLimitExceeded, mark that run FAILED with CLASSIFICATION_TASK_TIMEOUT.
Do not record that failure as PROVIDER_TIMEOUT. The two codes suggest different
remediation, and later operations need to tell them apart.

Do not expose provider stack traces or raw responses to the browser.

Use bounded transient retries for provider rate-limit, 5xx, network failures,
and PROVIDER_TIMEOUT.

Do not retry indefinitely.

A persistent failure ends the run as FAILED.

CLASSIFICATION_TASK_TIMEOUT is not a transient per-call retry. It ends the run.
Explicit user retry creates a new run.

A failed page-classification call still fails the whole run. Retry starts a
new run and repeats that work. Phase 4 does not resume a failed run at the
next page batch.

There is no stale-RUNNING sweeper in Phase 4. A worker killed without the soft
time limit can leave a run RUNNING. ensure returns that run. Backfill does not
adopt RUNNING rows and does not retry them.

    page 12 → BREAKER_DOCUMENT

        High

    [ Choose another type ]

Engineer clicks Accept.

    RevisionDocument.document_type = MIXED_DOCUMENT

    accepted_classification_prediction_id = <AI prediction id>

STEP 9

Revision 2 is later created from Revision 1.

The same immutable Document is inherited.

There is:

    NO new Document
    NO Phase 3 reprocessing
    NO duplicate AI classification

The new RevisionDocument carries forward:

    document_type = MIXED_DOCUMENT
    accepted_classification_prediction_id = same prediction

A future prompt/model version is deployed.

Engineer clicks:

    Reclassify

PowerForge creates a new classification run.

The previous run/predictions remain unchanged.

The new prediction does NOT alter the confirmed document type unless the
engineer explicitly accepts it.
