POWERFORGE — PHASE 4.5 IMPLEMENTATION
DOCUMENT WORKSPACE UI / UX REFACTOR

You are implementing a frontend-focused Phase 4.5 for PowerForge.

Phases 0–4 are complete.

The current revision-document workspace accumulated features incrementally across:

- Phase 2 document management
- Phase 3 document processing
- Phase 4 AI classification

The underlying architecture and backend behavior are correct, but the document
table has become visually congested and action-heavy.

Phase 4.5 must redesign the document workspace into a clean, professional,
engineering-oriented master-detail interface.

THIS IS PRIMARILY A FRONTEND INFORMATION-ARCHITECTURE REFACTOR.

Do not redesign Phase 2–4 domain models or backend workflows.

======================================================================
2. PURPOSE OF THIS REFACTOR
======================================================================

The current document table is carrying too many responsibilities.

It currently attempts to simultaneously present:

- filename
- size
- document number
- confirmed type
- AI suggestion
- AI confidence
- AI acceptance
- origin
- included/removed status
- processing status
- classification status
- added date
- page classification
- retry actions
- reclassify actions
- processing actions
- metadata actions
- download
- remove/restore

This produces:

- too many columns
- too many buttons
- poor visual hierarchy
- horizontal congestion
- nested workflows inside table cells
- difficulty scanning documents quickly
- increasingly poor scalability as future phases add more information

The new design principle is:

    ROWS COMMUNICATE STATE.
    DETAIL PANELS PERFORM WORK.

The document list should answer:

    "What documents are in this revision?"
    "What type are they?"
    "Which documents need attention?"

Detailed operations should happen in a selected-document detail surface.

======================================================================
9. STATE PRECEDENCE
======================================================================

Define deterministic presentation precedence.

A sensible default:

1. REMOVED
2. PROCESSING FAILED
3. PROCESSING IN PROGRESS
4. CLASSIFICATION FAILED
5. CLASSIFICATION IN PROGRESS
6. NEEDS REVIEW
7. READY

Define this as a reusable frontend derivation rather than scattered conditionals.

Suggested logic:

REMOVED:
    RevisionDocument.status == REMOVED

PROCESSING FAILED:
    Phase 3 latest processing state failed and no usable completed processing
    state is available as required by current API semantics

PROCESSING:
    Phase 3 processing pending/running

CLASSIFICATION FAILED:
    current/latest classification attempt failed
    AND document otherwise has usable Phase 3 processing

CLASSIFYING:
    classification attempt pending/running

NEEDS REVIEW:
    one or more review conditions below apply

READY:
    no issue/action currently requires attention

Do not alter backend state to implement this.

======================================================================
10. NEEDS REVIEW DEFINITION
======================================================================

Use Needs Review when human classification attention is useful.

Examples:

    confirmed document type is UNKNOWN
        AND usable AI suggestion exists

    confirmed type differs from AI suggestion

    AI suggests MIXED_DOCUMENT and the confirmed value has not been accepted

    AI suggestion exists and has not yet been accepted/manual-resolved

Do NOT mark every document with AI output as needing review if the confirmed
classification already clearly reflects the accepted prediction.

Exact logic should respect:

    accepted_classification_prediction_id

and current Phase 4 semantics.

======================================================================
54. DESIGN QUALITY BAR
======================================================================

The finished document workspace should feel:

    professional
    calm
    information-dense but not cluttered
    suitable for engineers working with dozens/hundreds of documents
    scalable to future PowerForge functionality

A user should be able to scan 30–50 documents quickly without each row becoming
a collection of buttons and badges.

The most important hierarchy should be immediately obvious:

    What is the document?
    What do we currently consider it?
    Does it need attention?

Everything else is secondary.
