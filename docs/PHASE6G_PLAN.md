# Phase 6G implementation plan

The approved [Phase 6G prompt](prompts/phase-6g-prompt.md) governs this work. The branch starts at `dea1ed3` on `main`, which includes the Phase 6F release handoff `a7c83a7`. Engineering and Tables keep separate runs, stage dependencies, provider calls and effective results. Both use exact committed preparation and spatial snapshots. Phase 5 and registry-v1 remain frozen.

## Current behavior

- The enhanced input projection excludes table-owned readings from Engineering. Its prose grounder requires one supported line, so separate label and value occurrences can fail even on a valid page. Layout membership alone does not establish ownership of engineering meaning.
- Recognition can publish an unresolved mention without making its possible registry attributes available to the attribute stage. The prose and table interpreters derive meaning from deterministic vocabulary before checking the provider proposal. An unfamiliar source field can be dropped despite having useful source evidence.
- The adapter collapses distinct invalid-response conditions into one error. Conversion uses that same error, and the existing output counts are only durable after publication. A completed attempt can produce zero candidates with little explanation in Run History.

## Semantic authority for successor profiles

OpenAI supplies the primary source-local interpretation of equipment, fields, values, units, qualifiers and relationships. An affirmative proposal is admissible when exact owned evidence supports the observations and the cited local context supports the proposed meaning without a material contradiction or unresolved ambiguity. Deterministic terminology can corroborate or identify contradictions. An alias hit is optional. A valid registry key and model confidence alone provide no contextual support.

For example, a manufacturer heading “magnetic isolation unit,” corroborated by a single nameplate with separate primary and secondary winding specifications, can support the two-winding transformer proposal. A source-local capacity field “continuous transfer duty” paired with `350` and a documented kVA heading can support the rated apparent power key even when the alias lookup fails. A bare `350`, competing value columns, or an unexplained manufacturer label provides insufficient support. An estimate at a specified temperature and base cannot be promoted to unconditional nominal impedance. A title-block designation can associate with the only documented device in scope, while a shared designation on a two-device sheet must remain unassigned without disambiguating source evidence.

PowerForge validates exact occurrences, source ownership, layout and scope limits, registry applicability, absence of contradicted claims and retention of essential qualifiers. It computes typed values and unit conversions with the existing exact registry normalization. Unsupported source assertions are rejected with diagnostics. Supported ambiguous meaning is retained as UNMAPPED, and established meaning with an invalid or unrepresentable value is retained as INVALID. Only MAPPED carries typed value slots. Model interpretations, original readings and normalized values retain separate provenance. No status confers engineer verification or establishes cross-document identity.

## Contracts and compatibility

- M1 adds an additive `extraction-stage-trace-v1` contract on enriched attempt settlement. Persist allowlisted stage outcomes, counts and safe validation paths separately from immutable execution plan metadata, existing numeric publication counts and provider usage. A one-to-one attempt row can capture failures as well as successes without overloading the retry plan or changing terminal legacy rows. Migration 0018 adds this table from 0017 with no backfill. New traces share the terminal transaction and existing lease fence. Existing run reads retain their shape with an optional trace. Dependency, cancellation and recovery states remain authoritative even where no trace was recorded.
- An explicit local developer capture can inspect one attempted enriched request in process, with a bounded exact source projection and parsed structured response plus committed output correlation. Access requires direct access to a disposable developer environment and invoking the execution path with a capture object. No ordinary API, worker configuration toggle or persistent raw capture. Keep provider bodies, images, credentials and SDK error text out of the capture and logs. Invalid responses without a structured object remain diagnosable to the extent the SDK exposes typed errors or response status.
- M2 will introduce versioned evidence parts and relationship bases for exact reading occurrences. Each part retains modality, offsets and artifact identity where supported. The server verifies bounded local structure and distinguishes textual designation, verified structure, visual report and unresolved association. Preserve separately grounded source facts when meaning or association is unresolved. Per-observation rejection operates inside a valid stage, while stage failure remains atomic.
- M3 will pin new enriched profile, prompt, response and interpretation identities. Engineering and Tables retain independent dispatch. Bounded registry context must be available when recognition abstains. Profiles v1–v6 keep their accepted resource identities and execution semantics, including when retried. Preserve source bytes for legacy identity checks where additive instrumentation touches hashed code.
- M4 will revise the successor Table Reconstruction and Interpretation contracts where fixtures justify it. Existing committed table structure remains the prerequisite for interpretation. Validate against exact spatial structure, preserve uncertainty, and keep installed devices distinct from provisioned positions. No extra provider calls.
- Any later schema extension must first demonstrate a gap in existing candidate, evidence and source-group contracts. Test upgrades from 0017 through head with representative stored and in-flight runs. Protect source reads and attempt diagnostics with the current revision-document membership checks.

## Review milestones

1. **M1 diagnostics.** Trace a synthetic split-field loss and classify invalid table responses in existing Run History. Verify empty success, failure, confidentiality, and historical access.
2. **M2 multi-reading grounding and retention.** Verify separate citations, modality fidelity, raw unmapped retention and rejection of fabricated or distant anchors.
3. **M3 AI-first interpretation.** Verify affirmative mappings when alias lookup fails and abstention for contradictory evidence. Test unresolved recognition, title-block tags, separate mentions and exact typed normalization.
4. **M4 Tables robustness.** Verify separate reconstruction and interpretation, invalid response handling and clear distinctions among installed and provisioned positions.
5. **M5 focused regression and handoff.** Verify representative synthetic cases, old-run read and retry compatibility, UI and worker integration. Document optional authorized private PDF evaluation. The original acceptance, production hardening and freeze goals belong to 6H, followed by 6.5 and Phase 7.

M1 ends at user review. Evidence relationship extensions, semantic admission rules and successor profile activation are decisions to validate at their corresponding milestone reviews. Keep the supplied real drawings private. Any live provider evaluation requires separate opt-in and approved source scope.
