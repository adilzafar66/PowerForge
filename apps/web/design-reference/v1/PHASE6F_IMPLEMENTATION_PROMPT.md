# PowerForge — Phase 6F: Documents-Integrated Extraction & Evidence UI

**Codex implementation assignment | Final Phase 6F reference: UX v1.19.2 (v1.19.1 simplified Candidates + comprehensive extraction by default)**

## 0. Objective and starting point

Implement Phase 6F as a production-grade, documents-integrated user experience for the Phase 6C/6D/6E extraction stack: selecting source documents and pages, preparing required native/OCR/layout source data automatically, starting opt-in engineering and/or table extraction, monitoring the resulting runs, and examining source-grounded engineering candidates (from prose and tables) in the existing document viewer. Support a single document, a selected set, all eligible documents in the revision, or a **confirmed document-classification group**.

**Do not create a standalone Extraction sidebar workspace.** Use the existing **Documents** register, its nonmodal inspector, the existing document viewer with `Document | Extraction Evidence` modes, and the approved three-step **Start extraction** modal (`Source → Enrichment → Extraction`). The Candidates view must use the approved **searchable source-group list → focused group candidates** flow (not one continuously expanding list).

The implementation requires limited, deliberately designed **backend orchestration work**: the current APIs start document-scoped enrichment/extraction runs, but no durable multi-document dependency coordinator currently drives preparation → layout → engineering/table extraction from one confirmation. Do not emulate that contract with fragile client-side promises or polling. Preserve existing per-document run execution semantics; add a durable aggregate intent only insofar as required for this UX.

**Baseline:** Verify repository status and use the *accepted Phase 6E M5 + M4 fixes* implementation, including migration `0016_enriched_extraction`, rather than assuming default `main` is up to date. As of prompt preparation, relevant Phase 6E code is on `codex/phase-6e-ocr-layout` at `a2e2ad222ef84d3751df6a88c58159eef73c20dc`; verify the current branch, merge status and latest accepted fixes before starting. Do not silently start against the older `main` snapshot. Make a dedicated `codex/phase-6f-extraction-ui` (or equivalent) feature branch from that verified baseline. Do not cherry-pick or rewrite frozen histories casually.

Before modifying code, inspect `docs/ROADMAP.md`, `docs/EXTRACTION.md`, `docs/PROVENANCE.md`, `docs/PHASE6C_HANDOFF.md`, `docs/PHASE6D_HANDOFF.md`, `docs/PHASE6E_HANDOFF.md`, accepted ADRs and the actual frontend/backend schemas. Produce a concise implementation plan divided into the milestones in §10, noting any necessary contract adjustment; then implement reviewable checkpoints. If an architectural choice affects source/run invariants, document it before implementation.


**Latest approved Phase 6F UX refinement (v1.19.2):** The backend profiles remain independent, but engineers should not be asked to choose which extraction family to run during ordinary operation. The single final Start extraction confirmation includes both families by default. `Advanced extraction settings` is collapsed initially; when opened, exactly two checked toggles can limit extraction to prose or tables, never neither. If one is deselected, show `Targeted extraction` (not `Comprehensive extraction`), update planned run count and external-processing consent, and preserve the user's deliberate choice across wizard back/forward. This supersedes any earlier Step 3 radio controls in v1.19.1 and supersedes v1.20 table-linking designs. Source selection, automatic enrichment, OCR overrides, combined candidate viewing, and Run History behavior otherwise remain v1.19.1.

A completed status is about the **run**, never verification of candidate truth.
- In the existing nonmodal **Document Details** panel, add **AI Extraction** directly below **AI Classification**, above **Document Metadata**. Show separate Engineering and Tables status, enrichment availability, recent runs, `Start extraction`, `View results`, and recovery actions only when backend allows. Show `Not extracted` plus action when no runs exist. Preserve the original inspector’s scroll, edit safeguards and selection behavior.
- Add row checkboxes with keyboard/a11y handling; preserve row-click to inspector. Contextual **Start extraction** toolbar appears only for selected eligible rows. Unaccepted AI classification suggestions must not silently choose documents. Snapshot the exact document IDs and source version/page selection at confirmation; changes to filters after submission must not expand or mutate the batch.
- Explicitly display skipped/ineligible/removed/unprocessed inputs and explain why. Do not perform classification acceptance or auto-classification as part of bulk extraction. ## 4. Start Extraction modal: same three steps, one confirmation

Preserve the approved wizard’s visual anatomy and straightforward navigation, accessible focus trapping, Escape/Cancel, independent per-document page ranges, back navigation, error retention and disabled invalid submissions.

**Step 1 — Source.** Show selected document(s), immutable source processing version, eligible page counts and editable per-document page ranges. Validate duplicates, malformed/out-of-bounds ranges, removed documents, unavailable page artifacts and backend caps. Support one, several, all eligible, and confirmed-classification-group selection. Present a stable review snapshot before submitting.

**Step 2 — Enrichment.** This is a **readiness and optional override view**, not an independent mandatory preparation action. For each document/page show whether completed compatible native/OCR preparation + spatial layout will be reused or must be prepared automatically after final confirmation. Reuse only when the backend can establish the **exact** pinned processing run, profile identity, page set, OCR selection, prepared result and layout result. Show `Ready/reuse`, `Will prepare automatically`, or `Unavailable/requires attention`; never claim compatibility from filename/date alone. Optional collapsed **Advanced OCR override** takes page numbers/ranges *within selected pages* and requests full-page OCR for those pages. An override can invalidate reuse and requires appropriate new/versioned preparation. The current **conservative hybrid-PDF OCR eligibility policy stays unchanged**; do not implement speculative region-specific OCR, text detection or new OCR thresholds in 6F.

**Step 3 — Extraction.** The primary, **default and recommended option is Comprehensive extraction**: include both engineering-text equipment/attribute extraction and tables/schedules automatically, requiring no extraction-family selection by ordinary engineers. Display an unambiguous `Comprehensive extraction` summary. Offer a **collapsed `Advanced extraction settings`** disclosure containing two independently labeled checkboxes: `Extract from engineering text` and `Extract from tables and schedules`. Both are initially enabled. Allow targeted engineering-only or tables-only execution for re-extraction/troubleshooting, but prevent both from being disabled. Recalculate the plan and consent disclosure when toggled. Keep two independently versioned underlying profile runs per document in comprehensive mode, one per document for targeted mode; do **not** introduce a combined OpenAI backend profile. These are user-facing options, not changes to 6C/6D/6E extraction semantics. Display selected documents, pages, reused vs scheduled preparation, expected individual run count, provider/model/profile availability, external processing disclosure and known usage/budget limits. Cost is `Unknown/not guaranteed` unless real, authoritative data can substantiate an estimate; never invent a dollar quote. Explicitly distinguish local preprocessing from paid/external OpenAI. A **single explicit final Start extraction** action authorizes all selected remote work. No hidden paid provider work on upload, selection, wizard navigation or profile-preview calls. Once confirmed, preparation/layout and dependent OpenAI proceed automatically under durable backend control. Don't require confirmation for each document. Do not begin OpenAI for a document until **every required exact source binding** for its selected pages is valid.

The frontend should display the durable operation ID, queued/running/completed/partial/blocked state, per-document child statuses, retries/cancel controls where permitted, and links to evidence. Closing the modal or navigating away cannot lose or silently cancel scheduled work.

## 5. Durable execution / bulk coordinator: narrow backend extension

This is a functional prerequisite, not optional UI polish. Existing Phase 6E APIs are document-scoped; create the smallest **durable, authorized server-side aggregate workflow** that satisfies single- and multi-document execution. It may be implemented as a new coordinator with persisted batch records and child-step references, or an equivalently robust design using the existing transactional run/scheduler mechanisms. Avoid introducing a second general-purpose job engine. Document its state machine and migration carefully.

Required invariants:

1. One admission request snapshots project/revision, **included revision-document IDs**, immutable document/source-processing identities, per-document page selection/OCR override, requested profile(s), explicit opt-in, and a bounded cost/provider-call/parallelism policy. Validate entire request before paid work; if partially eligible, present a deliberate review or deterministic per-item outcome rather than silently submitting a different plan.
2. Per document, reuse only fully compatible completed `source-preparation-v1` results. Schedule missing preparation, then exact `source-layout-v1` results for the prepared pages, then one engineering and/or one table extraction run with exact `enrichment_bindings`. **Never bypass source planning, source identity checks or versioned profiles.** Preserve all successful artifacts and immutable prior histories.
3. A durable scheduler/reconciler advances dependencies after backend state changes, including after API process restart, Celery delivery loss, duplicate delivery and client disconnection. Use existing transactional/admission patterns and worker queues. Ensure claimed steps are fenced, idempotent and recoverable; a retry must not automatically duplicate completed billable work. Concurrent identical requests must not accidentally multiply paid runs. Report ambiguous provider-call outcomes conservatively.
4. Bound fan-out, concurrency, pages, OCR workload, provider admissions and retries. Reuse existing per-profile limits; don't infer a guaranteed dollar ceiling from unknown pricing. Failed preparation blocks only its **dependent** profile runs; other documents can finish. Partial/failure/blocked statuses accurately enumerate successful, pending and failed child steps, with per-child retryability. Never describe a blocked OpenAI call as having started.
5. Batch cancellation is explicit and backend-authoritative; decide/document whether it requests cancellation of only unstarted children, also running children, or both. Respect existing run cancellation/lease semantics, preserve completed outputs and prevent stale publication. Re-extraction must be a distinct, explicitly authorized mode, not a side effect of polling/Retry UI.
6. Maintain revision-scoped membership authorization for every batch read/action and every child reference. Do not expose another project's children, raw object keys, provider credentials, stored external prompts, or unvalidated arbitrary URLs. Identity changes or removed documents after admission must be handled according to the server snapshot/authorization policy, not blindly followed from stale client state.
7. Keep standalone single-document extraction and existing Phase 6E endpoints operational; provide forward-compatible APIs/read models for aggregate operations and efficient Documents statuses. If an existing endpoint is extended, do so backwards-compatibly. Migrations must upgrade from 0016; document downgrade constraints before testing.

Prefer backend business logic independent of HTTP/Celery, deterministic tests with mocked providers, concise aggregate models, and an explicit transaction boundary. **Do not alter frozen 6C/6D/6E runtime identity inputs or change accepted prompts, eligibility rules, normalization, registry or source-evidence semantics.** Add versioned resources/profiles only if a genuine runtime change is unavoidable; prove old profiles and historical runs still reproduce.

## 6. Extraction Evidence viewer: scalable, truthful source navigation

Extend `document-viewer.tsx` and existing viewer shell, not a second independent renderer. Retain `Document | Extraction Evidence`, thumbnails, page selection, fit-width/page, zoom, pan, responsive operation and document metadata mode. The evidence mode has exactly **Candidates | Run history** in the existing right inspector, with a read-only unified Candidates view based on independently selected source-scoped run results (Engineering and Tables).

**Candidates (unified read-only presentation):** Display supported candidates from the selected effective Engineering prose run **and** selected effective Table extraction run together in one hierarchical source-group browser. This is a **read/view aggregation**, not merged extraction outputs, a combined provider run, or a physical-identity resolution. When both profiles have completed results, the default is the latest compatible/effective result for **each family independently**; if only one is available, show it without inventing completeness for the missing family. Preserve selected historical runs and effective-unit coverage when explicitly viewing history. Carry `run_id`, profile family, document/processing source and original `candidate_id`, `source_group_id` and citation/evidence identities through the read model. Group keys must include run identity (`run_id` + `source_group_id`), so coincidentally equal tags, values or local group labels do not merge. Distinct source observations may legitimately contain identical values; do not deduplicate by tag/value/page/attribute. Avoid displaying the same stored `(run_id, candidate_id)` twice due to pagination or aggregation. No new prose/table source-type filter, bidirectional candidate↔table navigation, or cross-tab synchronization. **Keep Engineering and Tables backend profiles, independent run semantics, table structure persistence and citations unchanged.**

Default to a compact **source-group register** with source-local labels/tags (when observed), equipment-type hints, page references, candidate counts, and subtle originating-run identification (e.g. `Engineering · Run 01` or `Tables · Run 02`). Provide server-backed **search by tag/type/attribute/value**, `All pages / Current page`, equipment-type-hint and `MAPPED / UNMAPPED / INVALID` filtering. Handle 50, 500+ groups using bounded server-side pagination/filtering or a suitable scalable read API; do not fetch all candidates or client-filter an unbounded corpus. Provide an **Ungrouped observations** bucket for source-grounded candidates with no reliable group. Separate counts from source identity: neither same tag text nor group name establishes a canonical equipment identity or cross-document merge. The v1.19 `Preview with 50 groups` control is a **prototype-only fixture**, not a production feature.

Selecting a group opens a focused list of **that group's candidates**, with Back returning to the exact search/filter/page/scroll state. Do not put all groups' cards in a single endless drawer. Selecting a candidate navigates to its actual source page and highlights only grounded, usable region/text geometry after applying the **correct source-frame→page-render transform**, including rotation and OCR/native coordinate provenance. A page-only/visual report navigates to the page **without inventing a rectangle**. Missing/unavailable artifact or geometry should render explicit, recoverable limitations. Preserve signed short-lived evidence access, exact source snippets, and strict run/document ownership; expired links must be refetched safely.

The **selected candidate expands in place**: readable field/value, mapping status/reason, original reading when different, source basis (`Native PDF`, `OCR`, or `Page-only`), unresolved physical identity, source highlighted indicator, and a collapsed `Source details` disclosure with verbatim text, context, source-local group and independent-verification limitations. **No permanent Selected Source Evidence card and no redundant Locate button** when already highlighted; offer `Locate source` only when needed. `MAPPED` means registry interpretation/normalization succeeded, not correct OCR or engineer approval. UNMAPPED reason codes can have accurate human-readable explanations (`unknown attribute`, `missing unit`, `unknown equipment context`, `ambiguous expression`); do not fabricate resolution. INVALID is a failed interpretation/normalization, not a failed job. Preserve raw data and distinction between unsupported observations vs valid cited candidates. No implicit canonical writes.

**Raw tables are secondary diagnostics, not a tab:** Remove the standalone Tables section from the primary viewer. Keep structured table data and source/header/cell evidence in the backend. If a table run has raw structural output, provide a small collapsed `Inspect raw table output (technical)` disclosure **inside that run's history detail**; this optional read-only fallback is for troubleshooting unmapped/unsupported cells. It must not recreate the main Tables navigation or add clickable table-cell-to-candidate links. Do not fabricate structures for unsupported/ambiguous layouts; render limitations plainly. Normal source review uses Candidates + the original PDF canvas and its evidence highlights.

**Run history:** Show immutable run history independently for Engineering, Tables and source enrichment, with profile/model, selected pages, attempt/coverage counts, partial outcomes, usage where available, error codes, retry/cancel eligibility and original source bindings. Run selection must be URL-addressable/bookmarkable and browser Back/Forward-safe, with stable document/revision scope. The candidate browser must make the selected effective run *pair* (one per profile family when available) unambiguous; never silently mix history with the latest. View old results while a new run is active; do not substitute the latest run's results into a historical selection.

**Scale/API:** Existing candidates endpoint supports `source_group_id` pagination/filtering but not necessarily efficient group-list search/current-page aggregation. Add a bounded server-side read model/query for group summaries if needed. Avoid N+1 evidence requests and huge unbounded result payloads. Filtered/empty/initial-error/refetch-error/active states must be explicit. Use safe URL/query state for selected run, group, candidate, page, tab, and viewer mode, without overwriting existing route contracts.

## 7. Mapping, registry, and strict phase boundaries

Keep the accepted source-extraction scope:

- **Mapped** = registry meaning/value normalization established; **Unmapped** = unresolved meaning/units/equipment/context; **Invalid** = interpretation/normalization failure. None mean engineer-approved. Raw values/evidence remain available when supported.
- Keep current Phase 6C/6D/6E extraction prompts and broad *relevant engineering observation* retention as implemented. We prefer **registry-first prioritization with conservative relevant-unmapped retention** as a **future measurable Phase 6G improvement**, not an unauthorized prompt/registry rewrite in this UI phase. Do not indiscriminately suppress out-of-registry fields or silently discard observations now. UI may show human-readable reasons from existing reason codes.
- Phase 6 must not infer physical-asset identity across sources (Phase 7), topology (Phase 8), cross-document conflict resolution (Phase 9), deterministic engineering checks (Phase 10), engineer acceptance/review (Phase 11), or canonical equipment/attribute mutation. Source-local `TX-101` is not automatically `Equipment.id`. Do not provide `Accept into model` controls.
- `system_frequency` and `system_phase_count` stay manual-only revision fields. Do not populate them from extraction.
- No Phase 6.5 Excel ingestion, no new OCR-region detection or automatic hybrid-image text heuristics, no source reprocessing redesign and no extracted-study-domain expansion.

## Final design decisions — do not re-litigate without an actual blocker

- **Extraction lives inside Documents; no separate sidebar tab.**
- **Three-step Start Extraction modal stays.** Enrichment is automatically scheduled after one final confirmation; no separate mandatory Run enrichment click.
- **Bulk extraction is essential**: individual, multi-select, all eligible, filtered and confirmed document type.
- **Engineering and Tables are distinct source-scoped run families**, even when initiated together.
- **Evidence drawer has only Candidates and Run history**, with a single hierarchical/searchable source-group browser containing prose and table-derived observations. No standalone Tables tab, no source-type filter or cross-view candidate/table linking, and no redundant permanent Selected Source Evidence panel.
- **No automatic cross-document equipment identity matching, engineer approval or canonical write.**
- **No new automatic hybrid-PDF OCR detection policy** in 6F; optional explicit whole-page override stays.
- **Registry-first extraction refinements deferred to evidence-based Phase 6G decisions**, while existing unknown/unmapped/invalid results remain visible and explainable.

Implement the approved behavior with engineering integrity and reusable components; retain autonomy in internal code organization and straightforward API naming as long as the stated contracts, UX and invariants are met.
